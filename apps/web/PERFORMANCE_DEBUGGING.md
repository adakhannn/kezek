# Отладка производительности web

Статус: действующий справочник по исходникам, сверка 2026-11-10. Аудитория: web-разработчик. Диагностические hooks проверены изолированными тестами; профилирование приложения не проводилось.

Измерение серверных операций и ограничения метрик описаны в [PERFORMANCE_MONITORING](../../PERFORMANCE_MONITORING.md), фактическая ёмкость — в [OPERATIONS](../../docs/OPERATIONS.md). Этот документ помогает исследовать один медленный экран; количество рендеров не даёт предела RPS.

## Сначала определить наблюдение

Для отдельной разрешённой диагностики зафиксируйте revision, режим dev/build, экран, действие, объём данных, устройство и сеть. Измеряйте одинаковый сценарий до и после изменения: задержку действия, число запросов, объём ответа, длительность рендера и итоговое состояние. Отделяйте серверное ожидание от клиентской обработки.

Повторный URL может быть ожидаемым polling или повтором после ошибки; отменённый запрос сам по себе не доказывает гонку. Проверьте инициатора запроса, зависимости эффекта и возможность устаревшему ответу перезаписать новое состояние. Memoization, debounce и отмена запросов применяются после установления причины; debounce денежных записей не обеспечивает атомарность.

## Инструменты, которые есть в репозитории

| Инструмент | Реальное поведение | Ограничение |
| --- | --- | --- |
| [useWhyDidYouRender](src/hooks/useWhyDidYouRender.ts) | После commit в development сравнивает props через Object.is, пишет изменения через общий redacting logger | Не использует JSON.stringify как dependency: функции и циклические объекты допустимы. Не полная трассировка рендеров; не передавать чувствительные значения |
| [useRenderCount](src/hooks/useRenderCount.ts) | Возвращает стабильный getter числа завершённых commits экземпляра; читать его в handler/effect. В development предупреждает после пятого, в остальных режимах getter возвращает 0 | Replay эффекта StrictMode не удваивает счётчик. Отброшенные renders не учитываются; порог 5 — эвристика, счётчик не измеряет длительность |
| [apiLogger](src/lib/apiLogger.ts) | Только явные вызовы logApiCall в development; хранит до 10 записей на METHOD/URL и отмечает повторы в пределах секунды | Не перехватывает fetch автоматически. Поиск потребителей на дату сверки не нашёл подключения logApiCall в приложении; число разных URL не ограничено |
| [PerformanceMonitor](src/components/dev/PerformanceMonitor.tsx) | В development отображает getApiStats и обновляет его каждые 2 секунды | Считает сохранённые записи apiLogger, а не все запросы или React renders. Подключения компонента в layout на дату сверки не найдено |
| [PerformanceTracking](src/components/PerformanceTracking.tsx) и [webVitals](src/lib/webVitals.ts) | Отдельная цепочка frontend telemetry | Не объединять её показатели с process-local серверной Map; HTTP приём метрики не гарантирует её сохранение |

React/браузерный profiler может дополнить измерение рендера и сети при разрешённом способе диагностики. Его результаты следует сохранять с контекстом сценария; ни цвет компонента, ни наличие React.memo сами по себе не являются приёмкой оптимизации.

## Команды и результат

Команды web находятся в [package.json](package.json), общие требования — в [CONTRIBUTING](../../CONTRIBUTING.md). В manifests нет готовых scripts analyze или check-console-logs; прежние примеры этих команд не были рабочей инструкцией. Build создаёт сборку, но сам по себе не является отчётом анализа bundle.

Вывод диагностики должен назвать узкое место, измеренное изменение и регрессии корректности. Для нагрузки отдельно нужны ресурсы, mix запросов и целостность данных. Открытые риски неограниченного параллелизма, локального cache и метрик сохраняются в [инженерном реестре](../../docs/ENGINEERING_FINDINGS.md).
