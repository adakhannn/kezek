# SECURITY.md — хранение и передача PII

Документ описывает, **какие данные считаются PII** (personally identifiable information) в Kezek, как они **хранятся**, **передаются** и **маскируются в логах**, а также как это связано с политикой сроков хранения (`DATA_RETENTION.md`).

## 1. Что считаем PII в Kezek

### 1.1. Основные PII-поля

- **Идентификаторы пользователей и клиентов:**
  - `profiles.id` (если может быть привязан к реальному человеку извне)
  - `profiles.full_name`
  - `profiles.phone`
  - `profiles.email`
- **Контактные данные в доменных сущностях:**
  - `bookings.client_name`
  - `bookings.client_phone`
  - `bookings.client_email`
  - `staff.full_name`
  - контактные поля в `staff_shifts`, `staff_shift_items` (если содержат имя/телефон клиента)
- **Идентификаторы мессенджеров и внешних систем:**
  - идентификаторы чатов/пользователей в WhatsApp-интеграции, если они могут быть сопоставлены с конкретным человеком.

### 1.2. Что НЕ считаем PII (в обычной конфигурации)

- Чисто **агрегированные метрики** и счётчики без указания конкретного пользователя:
  - суммарное количество бронирований / визитов / выручки;
  - данные в воронке (`funnel_events`) без прямых персональных полей.
- **Технические идентификаторы**, которые не позволяют однозначно идентифицировать человека сами по себе:
  - `booking_id` в логах (без имени/телефона/почты);
  - случайные `session_id`, если они не связаны напрямую с персональными данными.

> Если в лог или метрику добавляется новое поле, его нужно классифицировать как PII/не-PII и при необходимости добавить в соответствующий раздел.

## 2. Хранение PII в БД

Правила хранения PII описаны детальнее в `DATA_RETENTION.md`. Ключевые моменты:

- **Брони (`bookings`)**
  - PII: `client_name`, `client_phone`, `client_email`.
  - **Срок:** 7 лет с даты визита (`start_at`).
  - **После срока:** PII-анонимизация через функцию БД `anonymize_old_bookings_pii` — персональные поля очищаются / заменяются нейтральным значением, а технические данные брони (даты, суммы, статусы) сохраняются для отчётности.

- **Профили клиентов (`profiles`)**
  - PII: `full_name`, `phone`, `email` (если есть).
  - **Срок:** 3 года с момента последней активности (последняя бронь или другое действие).
  - **После срока:** для профилей, которые не являются сотрудниками и не имели активности 3+ года, PII-анонимизация через `anonymize_inactive_profiles_pii`.

- **Смены и позиции смен (`staff_shifts`, `staff_shift_items`)**
  - Финансовые и рабочие данные хранятся **7 лет** (учёт и споры).
  - Если в `staff_shift_items` используются поля с именем клиента, они могут быть включены в общую стратегию анонимизации (см. `DATA_RETENTION.md` §2.5).

Подробнее см. `DATA_RETENTION.md` (таблица сроков хранения и описание cron-задач).

## 3. Передача PII между сервисами

### 3.1. Внешние интеграции (WhatsApp, e-mail и т.п.)

- В вебхуках и исходящих запросах к внешним API передавать **минимально необходимый набор PII**:
  - для уведомлений — телефон и текст сообщения;
  - не отправлять в сторонние системы лишние поля (например, внутренние идентификаторы, которые не нужны внешнему провайдеру).
- В логах вебхуков не сохранять полные тексты сообщений, если там могут быть PII/чувствительные данные — только технический статус, коды ошибок, усечённые идентификаторы.

### 3.2. Внутренние API и фронтенд

- В **client-side код** (React, браузерные запросы) отдавать только те PII, которые реально нужны для экрана:
  - для списков и таблиц — можно возвращать обезличенные или сокращённые данные, если полное имя/телефон не требуются.
- В **админских** и **кабинетных** API убедиться, что:
  - RLS и бизнес-логику доступа проверяют, что пользователь видит только свои данные или данные своего бизнеса;
  - чувствительные поля не попадают в ответы, если они не нужны UI.

## 4. Маскирование PII в логах и метриках

Общая цель — в логах и метриках **не должно быть "сырых" PII**, если это не крайне необходимо для расследования инцидентов.

- При логировании ошибок и запросов:
  - **телефоны** логировать в маскированном виде: `+996***1234` или полностью удалить;
  - **e-mail** — маскировать: `u***@example.com`;
  - **имена** — по возможности не логировать, достаточно `booking_id`, `profile_id` и бизнес-идентификаторов.
- В `api_request_metrics` и других метриках:
  - хранить техническую информацию (метод, путь, статус, тайминги), **без PII**.
  - если необходимо привязать метрику к бизнесу или пользователю, использовать `biz_id`, `staff_id`, `booking_id`, но не имя/телефон.

Рекомендации по срокам хранения логов и метрик и их очистке/анонимизации описаны в `DATA_RETENTION.md` (§1–3).

## 5. Роль Supabase Service Role Key и RLS

`SUPABASE_SERVICE_ROLE_KEY` даёт **полный доступ к БД и обходит RLS**. При работе с PII:

- использовать его **только**:
  - в серверных компонентах;
  - в `route.ts` (API routes);
  - в серверных cron-задачах (например, `data-retention`).
- **никогда** не использовать:
  - в `'use client'` компонентах;
  - в браузерном коде;
  - в публичных эндпоинтах без дополнительной строгой авторизации.

Функция `getSupabaseServiceRoleKey()` уже защищает от вызова на клиенте:

```typescript
if (typeof window !== 'undefined') {
  throw new Error('SUPABASE_SERVICE_ROLE_KEY cannot be used in client-side code');
}
```

## 6. Чек-лист перед релизом / аудитом

Перед крупным релизом или аудитом безопасности стоит проверить:

1. **Классификация полей**
   - Все новые поля, связанные с пользователем/клиентом, отнесены либо к PII, либо к агрегированным данным.
   - При необходимости документ обновлён (раздел 1).

2. **Хранение и срок жизни**
   - Новые таблицы и поля учтены в `DATA_RETENTION.md` (срок, действие по истечении, реализация).
   - Cron-задачи для data-retention обновлены, если добавлены новые функции БД.

3. **Логи и метрики**
   - В логах и метриках нет "сырых" телефонов/e-mail/имён.
   - Для отладки используются либо ID, либо маскированные значения.

4. **Код**
   - `SUPABASE_SERVICE_ROLE_KEY` не используется в `'use client'` файлах.
   - Внешние интеграции не получают лишние PII-поля.

5. **Документация**
   - Этот документ (`SECURITY.md`) и `DATA_RETENTION.md` согласованы между собой.
