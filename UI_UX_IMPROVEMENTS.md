## 1. Клиентский опыт: “Мои записи” (web + mobile)

### 1.1. Разделение предстоящих и прошедших записей

- [x] 🟠 **UX-BOOKINGS-1**: Разделить список на “Предстоящие” и “История”
  - Web: в кабинете клиента сделать две вкладки/секции (предстоящие сверху, история ниже).
  - Mobile: в `CabinetScreen` визуально разделить предстоящие и прошедшие (табы или заголовки с группировкой по дате).
  - Обновить E2E/скриншоты, если есть привязка к текущему виду.

### 1.2. Быстрые действия по записи

- [x] 🟡 **UX-BOOKINGS-2**: Добавить быстрые действия рядом с записью
  - Для будущих записей: быстрые кнопки “Отменить”, “Повторить”, “Написать в WhatsApp/позвонить” (там, где это уместно).
  - Для прошедших: быстрый переход к отзыву (если поддерживается) или повторной записи.
  - Обеспечить, чтобы действия были доступны как на web, так и на mobile (минимум в деталях записи).

### 1.3. Ленточка статусов записи

- [x] 🟡 **UX-BOOKINGS-3**: Добавить короткий таймлайн статусов для записи
  - На экране деталей брони (web + mobile) показать цепочку: создано → подтверждено → завершено/отменено → промо применено (если было).
  - Подвязать статусы к уже существующим значениям (`hold`, `confirmed`, `paid`, `cancelled`, `no_show`).

## 2. Операторы и менеджеры: QuickDesk и dashboard

### 2.1. Режим “Сегодня за стойкой” vs “История”

- [x] 🟠 **UX-DESK-1**: Разделить QuickDesk на рабочий и исторический режимы
  - “Сегодня”: фокус на активных/ближайших бронях, быстрые действия (создать, отметить “пришёл/no-show”, отменить).
  - “История/поиск”: фильтры по дате/клиенту/статусу, менее агрессивный UI, можно грузить больше строк.

### 2.2. Командная панель для основных действий

- [x] 🟡 **UX-DESK-2**: Вынести главные действия в одну панель
  - Добавить сверху/сбоку панель с крупными кнопками: “Новая запись”, “Отметить пришёл”, “Отменить”, “Открыть смену/Закрыть смену (если релевантно)”. 
  - Сократить количество разбросанных по таблице мелких иконок без подписей.

### 2.3. Улучшить сообщения об ошибках в dashboard

- [x] 🟢 **UX-DESK-3**: Единый ErrorBanner для операторских экранов
  - Ввести компонент `ErrorBanner`/`Alert` для: нет доступа / ошибка валидации / внутренняя ошибка.
  - Использовать его в QuickDesk, staff‑финансах, сменах, вместо однотипных “ошибка” без контекста.

## 3. Mobile: Home и оффлайн‑режим

### 3.1. Персонализация домашнего экрана

- [x] 🟡 **UX-MOBILE-1**: Показать “Ближайшие записи” и “Недавние места” на Home
  - Блок “Ближайшие записи” (1–3 ближайших броней из кабинета) над списком бизнесов.
  - Блок “Недавние места”: 2–3 бизнеса, где пользователь недавно записывался.

### 3.2. Оффлайн‑состояние Home и бронирования

- [x] 🟠 **UX-MOBILE-2**: Добавить понятный оффлайн‑режим на Home и в бронировании
  - Связать отображение оффлайна с реальным статусом сети (`useNetworkStatus`, когда он будет реализован).
  - На Home: баннер “Нет подключения — список обновится при появлении сети” + optional кэш бизнесов (минимальный).
  - На шагах бронирования: при потере сети показывать явную ошибку и не сбрасывать уже выбранные шаги, разрешая повторную попытку.

## 4. Mobile: флоу бронирования

### 4.1. Индикатор прогресса по шагам

- [x] 🟡 **UX-MOBILE-3**: Добавить визуальный индикатор шагов в мобильном флоу
  - Показать прогресс “Шаг 1/5: филиал → 2/5: услуга → 3/5: мастер → 4/5: дата/время → 5/5: подтверждение”.
  - Обеспечить, чтобы переходы по шагам были предсказуемыми (назад/вперёд, сохранение введённых данных).

### 4.2. Устойчивость к ошибкам на поздних шагах

- [x] 🟠 **UX-MOBILE-4**: Сделать UX устойчивым к сетевым ошибкам на шаге времени/подтверждения
  - При сетевой ошибке на confirming шаге не сбрасывать весь флоу — оставить пользователя на том же шаге с сообщением “Нет сети / ошибка сервера, попробуйте ещё раз”.
  - Логировать ошибки так, чтобы можно было отследить проблемные точки (Sentry/лог‑служба).

## 5. Как использовать этот документ

1. При планировании дизайн‑итераций выбирать задачи с приоритетом 🔴/🟠, стараясь охватывать сразу и web, и mobile там, где это логично.
2. При выполнении задачи:
   - обновлять статус чекбокса,
   - при необходимости ссылаться на макеты/PR/issue.
3. Раз в квартал:
   - ревью документа вместе с `IMPROVEMENT_TASKS.md` и фактическими отзывами пользователей,
   - добавлять новые UI/UX‑задачи или закрывать устаревшие.
