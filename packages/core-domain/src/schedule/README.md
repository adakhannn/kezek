# Schedule Domain Module

Доменный модуль для работы с расписаниями и слотами.  
Содержит чистые функции без зависимостей от HTTP-слоя или Supabase-клиента.

> Основной расчёт свободных слотов (`get_free_slots_service_day_v2`) выполняется на стороне БД (SQL/RPC).  
> Этот модуль отвечает за пост‑обработку результатов и учёт временных переводов на фронтенде.

## Серверный фильтр мастера и страницы

С 10 ноября 2026 [миграция](../../../../supabase/migrations/20261110121000_staff_scoped_slots.sql) добавляет шестой аргумент `p_staff_id uuid` к single-service RPC. Все шесть аргументов в этой перегрузке обязательны. Web/mobile callers передают выбранного мастера до расчёта расписания. SQL проверяет активность, бизнес, эффективный филиал и доступность; resolver и ограничение БД на пересечение бронирований не меняются. Неизвестный/неактивный мастер, сотрудник другого бизнеса или отсутствие подходящего расписания дают пустой результат.

Публичные вызовы старого five-argument/defaults варианта, six-argument с `NULL` и complex RPC с `NULL` staff теперь явно отклоняются с `USE_PAGED_SLOTS`. Подписи остаются для служебной диагностики через service role. Это изменение контракта старых клиентов: сначала применяется миграция, затем выкатываются обновлённые клиенты; старый клиент должен обновиться, автоматического fallback на полный расчёт нет.

[Legacy surface migration](../../../../supabase/migrations/20261110140000_booking_legacy_surface.sql) также закрывает browser EXECUTE старого `get_free_slots_service_day(..., p_tz text)` без суффикса v2. У него нет runtime callers; оставленный публичным он позволял бы обойти ограниченный расчёт. Service role сохраняет диагностический доступ.

Для «любого мастера» public web использует `get_free_slots_page_v1`, возвращающий scalar JSON `{ slots, next_cursor }`. Одна страница содержит не более 100 слотов и вызывает resolver не более восьми сотрудников. Cursor версии 1 включает scope, staff ID и время; scope привязан к бизнесу/филиалу/дню/услуге или complex duration/мастеру. Неправильная структура или другой scope отклоняются. Перед cursor нет per-staff cutoff, который мог бы потерять поздние слоты; одинаковые интервалы одного мастера дедуплицируются, а разные мастера с одинаковым временем сохраняются.

Порядок страниц — staff ID, затем время. В пределах загруженных страниц UI сортирует время и сохраняет имена/выбор каждого мастера; глобально ближайший слот среди ещё не загруженных сотрудников не обещается. Загрузка следующей страницы явная. Пустая страница с cursor означает продолжение, а не отсутствие слотов. Ошибка продолжения сохраняет уже показанные варианты, повтор использует тот же cursor; смена фильтров отменяет право старого ответа менять список. Scalar JSON избегает тихого усечения таблицы ответа лимитом PostgREST. Это не snapshot всей выдачи: доступность между страницами может измениться, окончательную запись проверяет атомарная команда бронирования.

[Изолированный runner](../../../../scripts/test-staff-scoped-slots-isolated.cjs) проверяет совместимость служебного вызова, отказ публичного полного расчёта, scoped/paged права, блокирующие бронирования, cursor, пустые промежуточные страницы и полноту simple/complex выдачи. Последний локальный замер 10 ноября на PostgreSQL 16 с 1000 синтетическими сотрудниками и контролируемым resolver:

| Вызов | Вызовы resolver | Строки | EXPLAIN ANALYZE |
| --- | ---: | ---: | ---: |
| Выбранный мастер | 1 | 39 | 44,407 мс |
| Служебный полный расчёт | 1000 | 39 000 | 17 774,423 мс |
| Первая публичная страница | 3 | 100 | время отдельно не измерено |
| Страница недоступных сотрудников | 8 | 0 + cursor | время отдельно не измерено |

Runner выводит полный JSON планов. Таблица относится к одному запуску 12:43–12:44 UTC 10 ноября; параллельно шли другие изолированные Docker-проверки, CPU не был изолирован. Это локальные измерения и проверка числа операций; они не доказывают production RPS, работу реального resolver или общий предел нагрузки. Здесь не выполнялись remote rollout и браузерная проверка.

## Структура

- **`types.ts`** — типы для слотов, временных переводов и контекста фильтрации
- **`helpers.ts`** — чистые функции:
  - `resolveScheduleContext` — определение контекста расписания (временный перевод, целевой филиал)
  - `filterSlotsByContext` — фильтрация слотов по мастеру, филиалу и минимальному времени
  - `filterServicesForStaff` — фильтрация услуг по филиалу и привязке к мастеру (service_staff), с учётом «похожих» услуг при временном переводе
- **`index.ts`** — публичный API модуля

## Использование

### Импорт

```ts
import {
  type RawSlot,
  type Slot,
  type TemporaryTransfer,
  type StaffInfo,
  type ScheduleContext,
  type SlotFilterContext,
  type ServiceInfo,
  resolveScheduleContext,
  filterSlotsByContext,
  filterServicesForStaff,
} from '@core-domain/schedule';
```

### Пример: учёт временного перевода и фильтрация слотов

```ts
const scheduleCtx = resolveScheduleContext({
  staffId,
  dayStr,
  selectedBranchId: branchId,
  temporaryTransfers,
  staff,
});

const filteredSlots = filterSlotsByContext(allSlotsFromRpc, {
  staffId,
  branchId,
  targetBranchId: scheduleCtx.targetBranchId,
  isTemporaryTransfer: scheduleCtx.isTemporaryTransfer,
  minStart: new Date(Date.now() + 30 * 60 * 1000), // минимум через 30 минут
});
```

### Фильтрация услуг по мастеру и временному переводу

При временном переводе мастер может оказывать в филиале перевода услуги, «похожие» на привязанные к нему (одинаковые `name_ru` + `duration_min`). Используйте `filterServicesForStaff`:

```ts
const servicesForDesk = filterServicesForStaff({
  services,
  targetBranchId: scheduleContext.targetBranchId,
  staffId,
  serviceToStaffMap, // Map<service_id, Set<staff_id>>
  isTemporaryTransfer: scheduleContext.isTemporaryTransfer,
});
```

## Принципы

1. **Чистые функции** — модуль не делает сетевых запросов, не логирует и не работает с React.
2. **Повторное использование** — общая логика фильтрации слотов и учёта временных переводов используется:
   - в публичном потоке бронирования (`useSlotsLoader`);
   - на странице свободных слотов сотрудника в дашборде.
3. **Чёткий контракт** — вся завязанная на Supabase/HTTP логика остаётся в `apps/web`, а модуль оперирует только данными (массивы слотов, переводы, сотрудники).

## Интеграция с текущим кодом

Модуль подключён через TS path `@core-domain/*` и используется в:

- `apps/web/src/app/b/[slug]/hooks/useSlotsLoader.ts` — загрузка слотов для публичного бронирования;
- `apps/web/src/app/dashboard/staff/[id]/slots/Client.tsx` — отображение свободных слотов по сотруднику.

## Расширение

При изменении формата RPC или добавлении новой логики слотов:

1. Обновите тип `RawSlot` в `types.ts`, если структура результата RPC изменилась.
2. При необходимости адаптируйте `filterSlotsByContext` (например, учёт дополнительных статусов).
3. Если появятся новые сценарии (другие виды временных переводов/правил), добавьте отдельные функции‑помощники, не смешивая их с HTTP/RPC-кодом.
