## 5. Доменные ошибки как `Error('<CODE>')` и сравнение по message

**Файл(ы):**
- `packages/core-domain/src/booking/useCases.ts`
- `apps/web/src/lib/errors.ts`

**Наблюдение:**
- В доменных use‑case’ах ошибки кодируются через `new Error('BRANCH_NOT_FOUND_OR_INACTIVE')` и подобные строки.
- В web‑слое тип ошибки определяется через `isErrorType(e, type)` c проверкой `e.message === type`.
- Это хрупко и не поддерживается компилятором.

**Задачи:**
- [x] 🟠 **CODE-DOMAIN-ERRORS-1**: Заменить строковые `Error` на типизированный результат
  - Ввести тип вида:
    - `type BookingErrorKind = 'BRANCH_NOT_FOUND_OR_INACTIVE' | 'NO_ACTIVE_BRANCH_FOR_BIZ' | ...;`
    - `type BookingError = { kind: BookingErrorKind; message?: string }`.
  - Возвращать из use‑case либо `Result<Success, BookingError>`, либо бросать специальный `BookingError`‑объект.

- [x] 🟡 **CODE-DOMAIN-ERRORS-2**: Обновить web‑слой на работу с типизированными ошибками
  - В `apps/web/src/lib/errors.ts` переключаться по `err.kind`, а не по `message`.
  - Привести API‑эндпоинты к единому формату JSON‑ошибок.

**Предложение по решению (кратко):**
- Начать с одного ключевого use‑case (например, cancel/mark‑attendance), внедрить новый формат ошибок, затем постепенно распространить на остальные.
