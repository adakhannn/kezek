# Резервное копирование и восстановление БД

Документ описывает политику бэкапов для БД Kezek (Supabase/PostgreSQL) и рекомендации по периодической проверке восстановления.

## 1. Supabase: встроенные бэкапы

### Типы бэкапов

- **Логические (logical)** — дампы данных, доступны для небольших БД (обычно до ~15 GB) на планах Pro/Team без PITR. Можно скачать через Dashboard или `pg_dump`.
- **Физические (physical)** — используются при включённом PITR, для БД >15 GB или на Enterprise. При включении PITR ежедневные логические бэкапы отключаются.

### Point-in-Time Recovery (PITR)

- Доступен как дополнение на платных планах с физическими бэкапами.
- Позволяет восстановить БД на **любой момент времени** (низкий RPO).
- Восстановление выполняется через Dashboard (дата/время) или [Management API](https://supabase.com/docs/reference/api/v1-restore-pitr-backup).
- Время восстановления зависит от объёма WAL с последнего полного бэкапа и размера БД — фиксированного SLA нет.

### Где смотреть в Dashboard

1. **Project Settings → Database** — раздел Backups: тип бэкапов, расписание, включён ли PITR.
2. **Restore** — восстановление из PITR или из снапшота (если доступно) в текущий или новый проект.

### Клонирование проекта

На платных планах с физическими бэкапами можно создать **клон проекта** (Restore to new project) — новый независимый проект с копией схемы, данных и Auth. Удобно для staging или проверки восстановления без затрагивания продакшена.

## 2. Рекомендуемая политика

| Элемент | Рекомендация |
|--------|----------------|
| **Тип бэкапов** | На продакшене предпочтительно PITR (если доступен по плану), чтобы минимизировать потерю данных (RPO). |
| **Retention** | Ориентироваться на настройки Supabase по плану (обычно 7–30 дней). При необходимости длительного хранения — периодический экспорт в своё хранилище (см. ниже). |
| **RPO/RTO** | Зафиксировать целевые значения (например, RPO ≤ 1 ч, RTO ≤ 4 ч) и проверять их при тестах восстановления. |

---

## 3. Дополнительный экспорт (опционально)

Если нужны независимые копии или длительное хранение:

- **pg_dump** через подключение к БД (connection string из Dashboard → Project Settings → Database). Экспорт можно автоматизировать в CI/cron и сохранять в S3/GCS или другой объектный сторедж.
- **Supabase CLI** — при включённом PITR логические бэкапы через Dashboard могут быть отключены; экспорт через CLI или прямой `pg_dump` остаётся вариантом.

## 4. Периодическая проверка восстановления

Чтобы убедиться, что восстановление реально работает:

| Частота | Действие |
|--------|----------|
| **Не реже 1 раза в год** | Восстановление из PITR (или из снапшота) в **новый проект** (clone/restore to new project). Проверить доступность приложения к новой БД, целостность ключевых таблиц и миграций. |
| **После крупных миграций** | По возможности проверить восстановление на клоне перед применением рискованных изменений в проде. |
| **Чек-лист проверки** | После восстановления: запуск приложения против восстановленной БД, проверка логина, выбор бизнеса, создание/просмотр брони, проверка рейтингов и критичных RPC. |

Результаты проверки (дата, тип восстановления, итог) целесообразно фиксировать (например, в CHANGELOG или внутреннем runbook).

---

## 5. Свой Postgres (не Supabase)

При переходе на свой инстанс PostgreSQL:

- Настроить **ежедневные логические или физические бэкапы** (pg_dump, WAL-G, Barman и т.п.) с хранением вне основного сервера.
- По необходимости включить **PITR** (непрерывная архивация WAL).
- Описать процедуру восстановления (из какого бэкапа, порядок применения WAL, проверки после восстановления) в отдельном runbook и проводить тесты восстановления не реже раза в год.
