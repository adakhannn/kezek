# Supabase: схема и подготовка окружения

Статус: действующий справочник репозитория. Обновлено 16 ноября 2026. Ответственная роль: сопровождающий БД; конкретный исполнитель операций назначается в отдельной задаче.

Первый запуск приложения описан в [GETTING_STARTED.md](../GETTING_STARTED.md), эксплуатационные зависимости — в [OPERATIONS.md](../docs/OPERATIONS.md).

## Baseline и чистая установка

Исходные таблицы, `booking_status` и `is_super_admin()` когда-то создавались вне миграций, поэтому старая цепочка не поднимала пустую БД. 16 ноября 2026 она заменена squash-ом:

- [20261009110000_prod_baseline.sql](migrations/20261009110000_prod_baseline.sql) — schema-only дамп прода (`supabase db dump`, без данных) на момент, когда история прода заканчивалась версией 20261009110000. Файл не редактируется: изменения схемы — только новыми миграциями;
- [20261009110001_reference_data.sql](migrations/20261009110001_reference_data.sql) — справочные строки (роли, активная конфигурация рейтинга), идемпотентно;
- дальше — миграции, ещё не применённые на проде.

Проверено локально и в CI (`db_bootstrap`): `supabase start` / `supabase db reset` поднимают baseline, все миграции и [seed](seed.sql) с нуля, а [типы](../apps/web/src/types/supabase.ts) совпадают со схемой (`pnpm check:db-types`).

Локальный стек: `pnpm db:start:check` (без Studio/Realtime и прочих необязательных сервисов), затем `pnpm generate:db-types` после новых миграций. `project_id` в [config.toml](config.toml) — `kezek`: `db reset` в этой папке стирает локальную БД этого стека.

### История миграций прода

**Синхронизировано и применено 16 ноября 2026.** 136 версий старой цепочки (включая alias `20260731082333`) помечены `reverted` через `supabase migration repair` — это правка только служебной таблицы истории; `20261009110000` остаётся applied как baseline. Затем `supabase db push` применил 24 миграции от `20261009110001` до `20261116120000`; `supabase migration list` показывает совпадение 25 локальных и удалённых версий. Перед применением снята резервная копия (schema, roles, data с auth/public/storage) вне репозитория — у проекта нет скачиваемых бэкапов и PITR. Дальнейшие изменения — обычным `supabase db push`.

## Окружения и доступ

В документации прежней WEB-кампании указан project ref `beulnmftzbmtbdlgurht`. Это идентификатор использованного окружения, а не разрешение на CLI, SQL, API или production-доступ. Для кампании действуют ограничения [WEB_AGENT_HANDOFF.md](../docs/WEB_AGENT_HANDOFF.md), включая доступ к Supabase только через обычный UI. Кампания закрыта, `kezek` — PAUSED.

Редактура документов 30 октября не запускает серверы, миграции, seed, reset, backup или restore. В этой задаче запрещён и удалённый reset. Для будущей операции нужны явно определённые цель и доступ; источник истины о применённых миграциях — состояние выбранной БД и его проверенные evidence, не имя SQL-файла.

## Подготовка будущей задачи по БД

1. Установить точное dev/staging/production-окружение и разрешённый способ доступа; не выводить ключи или connection strings в отчёт.
2. Определить происхождение базовой схемы, версию PostgreSQL и установленную историю миграций. Локальный [config.toml](config.toml) задаёт PostgreSQL 17; версия удалённого проекта здесь не проверена.
3. Сопоставить схему, функции, grants/RLS и исходники по [порядку миграций](APPLY_MIGRATIONS.md).
4. Для нового стенда сначала закрыть пробел baseline и подтвердить воспроизводимое восстановление в изоляции.
5. Назначить проверки результата и условия остановки до изменения данных.

Docker требуется для локального Supabase. Пакет CLI объявлен в корневом [package.json](../package.json); используйте согласованную с lockfile версию, а не произвольный `@latest` из старой инструкции.

## Типы приложения

[apps/web/src/types/supabase.ts](../apps/web/src/types/supabase.ts) генерируется из локального стека (baseline + миграции) скриптом [generate-db-types.mjs](../scripts/generate-db-types.mjs); CI проверяет, что файл не отстаёт от миграций. Фабрики клиентов web (`supabaseHelpers`, `supabaseService`) создают клиентов с `<Database>`, поэтому запросы через них проверяются типами. Клиенты, которые создаются прямо в старых admin-роутах и страницах, пока не типизированы. Общие имена переменных подключения перечислены в [ENV_GUIDE.md](../ENV_GUIDE.md); значения секретов в документацию не включаются.
