# Миграции БД: порядок работы и исторические ссылки

Статус: действующий порядок подготовки; исторические примеры отделены ниже. Обновлено 10 ноября 2026. Ответственная роль: сопровождающий БД совместно с разработчиком изменения.

Этот документ сам по себе не разрешает применение миграций. Новый запрос владельца разрешил исправления и работу с существующим тестовым Supabase; результаты локальной проверки и фактическое удалённое применение различаются. Для прежней WEB-кампании сохраняются ограничения [handoff](../docs/WEB_AGENT_HANDOFF.md), кампания закрыта и automation — PAUSED.

## Прежде чем выбирать миграции

**Полный baseline схемы в репозитории отсутствует.** Ранние миграции требуют ранее созданные таблицы и `booking_status`; [подробное описание](README.md). Поэтому ни `db reset`, ни применение всего каталога к пустому проекту не являются готовой процедурой развёртывания.

Для отдельной разрешённой DB-задачи зафиксируйте:

| Вопрос | Что требуется установить |
| --- | --- |
| Цель | Точный проект/окружение и предел доступа; локальный конфиг не подтверждает remote state |
| Исходная схема | Происхождение baseline, версия PostgreSQL, extensions, функции, таблицы, grants/RLS |
| История | Какие версии действительно применены и соответствуют ли они текущим файлам |
| Изменение | Точный набор SQL и зависимостей, ожидаемые блокировки, изменения данных и совместимость приложения |
| Восстановление | Доступная проверенная копия либо иной согласованный способ восстановления, с условиями применения |
| Проверка | Наблюдаемые результаты и stop condition; наличие функции по имени недостаточно |

Если история и фактическая схема расходятся, сначала разберите расхождение. Нельзя просто отметить миграции применёнными, чтобы CLI пропустил их.

## Проверенная исходная среда 10 ноября 2026

Владелец подтвердил, что связанный проект `kezek` используется как тестовый. Через read-only SQL получены схема, ACL, ограничения и история; фактический сервер — PostgreSQL 17.4. Сохранены частные schema-only дампы `public` + `auth` и резервная копия данных `public`. Эти файлы не публикуются в Git: определения функций также могут содержать чувствительные значения.

На отдельном контейнере PostgreSQL 17, без сетевого доступа и портов, восстановлены исходные схемы и данные. Для внешних ключей восстановлены только идентификаторы Auth пользователей; пароли, токены и действующие сессии не переносились. При replay сохраняются реальные constraints, RLS и triggers. Это проверка совместимости с зафиксированной схемой, а не готовый чистый bootstrap всего Supabase из checkout.

Установлены два расхождения истории:

- Remote `20260731082333`, имя `public_business_contacts`: сохранённый statement совпал с локальным [20260731010000](migrations/20260731010000_public_business_contacts.sql) после нормализации комментариев/пробелов. Повторять backfill контактов не требуется.
- Локальная [20261015075000](migrations/20261015075000_work_locations_include_home_days.sql) не записана в remote history, но действующее тело `read_staff_work_locations` уже включает home days и соответствует этому изменению; ACL остался service-only. Отсутствующий номер не доказывает отсутствующее поведение.

Поэтому **не запускать общий `db push --include-all`** на основании списка отсутствующих номеров. История ещё требует отдельного согласованного reconciliation; эти наблюдения не означают, что она уже исправлена. Новые ноябрьские миграции проверяют явным упорядоченным набором и фиксируют hash каждого файла. Изменение ACL/protocol требует согласованного rollout web/mobile; применение SQL без совместимого приложения может намеренно закрыть старые пути.

## Контролируемое применение

1. Подготовить план для конкретного окружения и SQL-набор для review. Не выбирать миграции по старому списку «следующих шагов».
2. На согласованном изолированном стенде проверить baseline и последовательность миграций. Стенд должен исключать случайное обращение к рабочим данным и отправку реальных уведомлений.
3. Проверить не только DDL, но и изменения данных, права выполнения `SECURITY DEFINER`, policies, constraints, индексы и зависимости RPC. Следующая миграция может переопределять функцию из предыдущей.
4. Для разрешённого применения сохранить результат выполнения, версию приложения и состояние истории. Не подменять факт выполнения записью в сводном документе.
5. Проверить выбранные инварианты и критичные сценарии допустимым методом. Зафиксировать ошибки, частичное выполнение и решение о восстановлении до продолжения.

CLI и SQL Editor — способы выполнения, а не взаимозаменяемые способы доказать результат. Ручное выполнение допустимо только как часть точного плана с последующей сверкой схемы и истории. Старое предложение вручную добавлять строки в `supabase_migrations.schema_migrations` как «опциональный» шаг отменено: такая запись сама по себе не выполняет SQL и может скрыть расхождение.

## Ошибки и условия остановки

- `relation already exists`, `column does not exist` или ошибка policy требуют проверки конкретного statement и исходной схемы. Их нельзя объявлять нормальными по одному тексту сообщения.
- Ошибка CLI не разрешает повторить весь файл через другой интерфейс: часть изменений могла быть применена, а операции с данными могут быть неповторяемыми.
- Для ошибки `cannot insert multiple commands into a prepared statement` сначала установить версию инструмента, способ вызова и точный неисполненный statement. Старые ручные обходы не являются актуальной диагностикой.
- Не использовать reset, `--include-all`, слепое обновление истории или исправление финансовых данных для устранения неизвестной ошибки миграции.

Историческая проблема `hours_worked` и ограничения старого исправления описаны в [FIX_BEFORE_MIGRATION.md](FIX_BEFORE_MIGRATION.md). Восстановление — в [BACKUP_AND_RESTORE.md](BACKUP_AND_RESTORE.md).
