# Задачи на будущее: максимальное улучшение проекта и кода

**Назначение:** единый бэклог задач для поэтапного улучшения кодовой базы, архитектуры, тестов, документации и UX. Задачи можно брать в спринты или выполнять по мере приоритета.

Остальные списки задач (REFACTOR_TASKS, IMPROVEMENT_TASKS, TASKS) архивированы; см. [docs/archive/](docs/archive/).

**Связь с другими документами:**
- Текущее состояние и уже закрытые проблемы — `PROJECT_REVIEW.md`, `EVOLUTION_TECH_PLAN.md`
- Планирование спринта по модулям — `FEATURE_MATRIX.md`
- Конкретные риски кабинета владельца — `OWNER_CABINET_RISKS_AND_IMPROVEMENTS_TASKS.md`

**Легенда приоритетов:**
- **P0** — критично для качества/безопасности, делать в первую очередь
- **P1** — высокий приоритет, заметно улучшает проект
- **P2** — средний приоритет, желательно при наличии времени
- **P3** — низкий приоритет, долгосрочные улучшения

**Статус задач:** при выполнении помечать `[x]`, при отмене — `[~]` с пояснением.

- **2.2.1 Доменные слои (`core-domain`, `shared-client`)**: пройтись по `packages/core-domain` и `packages/shared-client`, убрать `any` из публичных API, завести явные типы/интерфейсы (DTO, use-case input/output). *(выполнено)*.
- **2.2.2 API и инфраструктура (`apps/web/src/lib`, API routes)**: типизировать хелперы (`authBiz`, `apiMetrics`, `rateLimit`, `apiErrorHandler`), заменить `any` на осмысленные типы, где это не внешний SDK. *(выполнено для указанных хелперов и текущих API routes — `any` и `@ts-expect-error` отсутствуют; для Supabase‑типов см. 2.2.3)*.
- **2.2.3 Supabase/OpenAPI интеграции**: там, где `@ts-expect-error` прикрывает вызовы Supabase/RPC или OpenAPI‑клиента, расширить типы (`Database`, сгенерированные SDK) и удалить комментарии, оставив `@ts-expect-error` только там, где типовая дыра объективно не закрывается. *(выполнено: в приложении нет `@ts-expect-error` вокруг Supabase/OpenAPI; оставшиеся `@ts-expect-error` используются только в тестах для частичных моков и не влияют на типобезопасность прод-кода).*
