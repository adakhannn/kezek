# user_current_business — модель выбора и границы инвариантов

Статус: справочник разработчика, сверено по исходникам **1 ноября 2026**. Сопровождение: разработчики auth/business-контекста. Документ различает ограничения репозиторной схемы, поведение сервисов и требования, которые не обеспечены всей цепочкой. Миграции и целевая БД этой работой не запускались и не проверялись.

Алгоритм manager resolver — [BIZ_CONTEXT_RESOLVER_ADR](BIZ_CONTEXT_RESOLVER_ADR.md). HTTP-контракты чтения/выбора — [BUSINESS_WORKFLOWS](api/BUSINESS_WORKFLOWS.md#контекст-бизнеса-и-данные-кабинета). Термины ролей — [GLOSSARY](GLOSSARY.md#роли-и-кабинеты).

## Назначение

user_current_business хранит последний выбранный бизнес пользователя. Это кандидат контекста для кабинета, а не назначение роли и не подтверждение доступа. Отсутствие строки, ошибка её чтения, выбранный бизнес без прав и несколько доступных бизнесов — разные состояния, хотя отдельные пути сейчас различают их не полностью.

## Что задано в репозиторной схеме

Источник — [миграция создания](../supabase/migrations/20260224000000_create_user_current_business.sql). Это определение через CREATE TABLE IF NOT EXISTS, а не подтверждение того, что эти ограничения присутствуют в уже установленной таблице.

| Ограничение | Что оно обеспечивает при наличии в БД | Чего не обеспечивает |
| --- | --- | --- |
| user_id PRIMARY KEY | Не более одной строки выбора на пользователя | Наличие строки для каждого пользователя или сохранение выбора resolver-ом |
| user_id REFERENCES auth.users ON DELETE CASCADE | Удаление выбора при удалении пользователя | Очистку при изменении роли |
| biz_id NOT NULL REFERENCES businesses ON DELETE CASCADE | Существование связанного бизнеса и удаление выбора при его физическом удалении | Очистку при изменении owner_id, роли, одобрения или активности |
| updated_at и BEFORE UPDATE trigger | Метку времени обновления строки | Историю всех выборов или аудит авторизации |
| RLS для authenticated | SELECT/INSERT/UPDATE/DELETE собственной строки по user_id = auth.uid() | Принадлежность выбранного biz_id разрешённым бизнесам: такого условия эти политики не содержат |

Следовательно, даже корректная внешняя ссылка не доказывает право пользователя управлять бизнесом. Привилегированные клиенты также требуют отдельной проверки полномочий в вызывающем коде; RLS собственной строки не является изоляцией всего бизнесового API.

## Чтение и явный выбор через API

[getCurrentBusinessState](../apps/web/src/lib/currentBusinessService.ts) возвращает сохранённый currentBizId отдельно от списка businesses. Список объединяет owner_id пользователя и роли owner/admin/manager с biz_id. Сохранённое значение не пересекается со списком перед возвратом; ошибки некоторых выборок игнорируются, поэтому успешный ответ может быть неполным.

[setCurrentBusinessState](../apps/web/src/lib/currentBusinessService.ts) проверяет существование бизнеса, затем owner_id либо owner/admin/manager-роль. После этого выполняет upsert по user_id. Это одна запись выбора, но проверка доступа и запись — отдельные запросы без общей транзакции; конкурентное снятие роли между ними не исключено. Отдельного super_admin-допуска этот сервис не содержит.

HTTP использует service client с fallback на пользовательский при невозможности его создать; источник — [currentBusinessHttpService](../apps/web/src/lib/currentBusinessHttpService.ts). Поля, ошибки и limiter описаны в API-справочнике. Успешный выбор не выдаёт роль и не обещает успешный следующий запрос к кабинету.

## Как resolver использует выбор

Точный порядок — [ADR](BIZ_CONTEXT_RESOLVER_ADR.md#2-приоритеты-выбора-бизнеса); основные различия:

| Состояние | Наблюдённое поведение |
| --- | --- |
| Обычный пользователь; сохранённый bizId и owner/admin/manager в user_roles | Выбранный бизнес принимается |
| Сохранённый bizId, но подходящей роли в user_roles нет | Автоподбор блокируется, возвращается NO_BIZ_ACCESS; строка выбора не очищается |
| Пользователь является owner_id, но для уже выбранного бизнеса нет соответствующей роли | Явный setter разрешает выбор по owner_id, а current-ветка resolver его не принимает; fallback owner_id не запускается при обнаруженной строке |
| Строка не прочитана / bizId отсутствует | Автоподбор по ролям, затем owner_id. Ошибка чтения current-строки отдельно не обрабатывается и может попасть в эту ветку |
| Несколько подходящих бизнесов, сохранённого выбора нет | Resolver выбирает первый по детерминированной сортировке; обязательного экрана выбора внутри него нет |
| Super-admin по RPC | Выбранный существующий бизнес либо fallback slug=kezek; это отдельная стратегия |

Resolver не пишет автоматически выбранный бизнес в user_current_business и не удаляет устаревшую строку. Наличие UI-helper [shouldRedirectToSelectBusiness](../apps/web/src/lib/cabinetAccess.ts), возвращающего true для нескольких бизнесов без выбора, не меняет алгоритм resolver и не доказывает, что каждый вход проходит этот helper.

Текущий бизнес без manager-роли не означает, что бизнесов у пользователя вообще нет. И наоборот, список доступных бизнесов в UI не гарантирует, что выбранный контекст пройдёт другую проверку. Staff — отдельная роль; [MANAGER_ROLE_KEYS](../apps/web/src/lib/userRoleProfile.ts) содержит только owner/admin/manager.

## Исторический backfill

[Миграция backfill](../supabase/migrations/20260224001000_backfill_user_current_business.sql) выбирает минимальный biz_id из manager-ролей, иначе минимальный id владения, и вставляет значение только пользователям без строки. Она не удаляет дубликаты, не исправляет уже существующий неверный выбор и не поддерживает соответствие ролям непрерывно. Наличие файла не означает его применение в среде.

## Требования, которые нельзя считать общей гарантией

| Требование | Граница текущей реализации |
| --- | --- |
| Один алгоритм авторизации для списка, setter и resolver | Наблюдается расхождение owner_id и current-role веток, отдельная стратегия super-admin |
| При потере доступа очистить выбор и потребовать новый | Current-ветка прекращает подбор, но сама строку не очищает и UI-переход не выполняет |
| При нескольких бизнесах всегда требовать явный выбор | Resolver допускает автоподбор; UI-helper и вызывающий маршрут нужно оценивать отдельно |
| Не путать недоступность сервисов с отсутствием прав | Resolver различает auth-сбой, но некоторые чтения БД игнорируют error, а withManagerContext преобразует SERVICE_UNAVAILABLE в 403; см. ADR |
| Изменение роли и выбор бизнес-контекста согласованы атомарно | Setter выполняет проверку и upsert отдельно; политика выбора сама бизнесовые роли не проверяет |

Это границы для будущего изменения и приёмки, а не команды очистки данных. Проверка должна учитывать owner-only, role-only, утрату роли, stale current, ошибки чтения и конкурентное изменение доступа. Существующие тестовые исходники: [currentBusinessService](../apps/web/src/__tests__/lib/currentBusinessService.test.ts), [bizContextResolver](../apps/web/src/__tests__/lib/bizContextResolver.test.ts). Их выполнение и deployed constraints в этой редакции не подтверждались; дальнейшая продуктовая работа требует отдельной задачи по [CONTRIBUTING](../CONTRIBUTING.md).
