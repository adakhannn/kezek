## Архитектура и границы доверия

- `TelegramBotLink`: диалог, локально генерируемый QR, ожидание с отменой запросов,
  проверка имени/username/ID, обязательное финальное подтверждение. Cookies Telegram
  не используются: аккаунт выбирается в приложении Telegram.
- `/api/auth/telegram/profile-link`: проверка Origin и действующей серверной сессии;
  owner берётся только из сессии. Отдельные пользовательские лимиты для создания,
  проверки статуса, отмены и завершения. Ответы не кешируются.
- `telegramProfileLinkService`: криптографическая 192-битная ссылка, в базе только SHA-256.
  Ни session exchange, ни автоматическое создание пользователя здесь не используются.
- `telegramProfileLinkWebhookService`: отдельное пространство команд `kl1_` / `kl1:`;
  только личный чат и Telegram identity из проверенного webhook. Общий webhook
  обязательно требует `TELEGRAM_WEBHOOK_SECRET`, даже если функция выключена.
- `telegram_profile_link_attempts`: RLS, доступ только service_role, TTL пять минут.
  Состояния: pending → approved → consumed; альтернативно cancelled/expired.
  Первый Telegram, открывший ссылку, фиксируется; для смены создаётся новая ссылка.
- RPC `transition_telegram_profile_link`: блокировка запроса и профиля, проверка
  владельца и выбранного Telegram, запрет переноса занятого аккаунта и замены текущей
  привязки. Профиль, auth.users metadata и consumed записываются одной транзакцией.
  Повтор завершения той же операции идемпотентен. Подтверждение бота само по себе
  не меняет профиль. Профиль видит Telegram identity только после согласия в боте.

## Согласуемое применение

1. Выполнено 2026-09-16: применена **только** миграция
   `supabase/migrations/20260916120000_telegram_profile_link_attempts.sql` через
   согласованный процесс. Не запускать все накопленные локальные миграции.
   Миграция добавляет таблицу и две функции; существующие привязки не переносит.
2. Настроить тестового бота отдельно от рабочего. Указать криптографически случайный
   `TELEGRAM_WEBHOOK_SECRET` в локальном защищённом конфиге и тот же `secret_token`
   при Telegram `setWebhook`. URL — текущий HTTPS-туннель + `/api/webhooks/telegram`.
   Включить updates `message` и `callback_query`, не удалять накопленные updates.
   Сначала проверить `getMe` / `getWebhookInfo`, чтобы не перезаписать webhook рабочего бота.
3. После проверки схемы и webhook установить `NEXT_PUBLIC_TELEGRAM_BOT_LINK_ENABLED=true`
   и перезапустить локальное приложение. Для production public-переменная требует пересборки.
   При смене туннеля обновлять webhook; настройка домена legacy Login Widget этому
   бот-сценарию не нужна.
4. Пройти ручные сценарии ниже. Только после этого отдельно согласовать production rollout.
5. Подключить `select public.cleanup_telegram_profile_links()` к ежедневному обслуживанию:
   удаляются запросы, истёкшие больше суток назад. Function доступна только service_role.

Откат включения: убрать флаг и перезапустить/пересобрать приложение. Таблицу не удалять,
существующие профили не откатывать. Неподтверждённые запросы истекают автоматически по TTL.

## Ручная приёмка

- Открыть бота с нужного аккаунта / по QR с телефона; до финальной кнопки в Kezek
  профиль не должен меняться. Имя, username и ID должны соответствовать выбранному аккаунту.
- Открыть ошибочным аккаунтом → новая ссылка → правильный аккаунт. Старая ссылка не работает.
- Telegram уже принадлежит другому Kezek: понятная ошибка, обе привязки сохранены.
- Отмена в боте/браузере, истечение пяти минут, обрыв сети, повтор завершения.
- Выход из Kezek/смена пользователя во время ожидания: другой профиль не может завершить запрос.
- Два параллельных подключения одного Telegram: только одно успешно.
- Независимость лимитов Telegram, WhatsApp и polling.

## Автоматические проверки

Jest: `telegramProfileLinkHttpService`, `telegramProfileLinkWebhookService`,
`telegramProfileLinkWebhookAuth`, `TelegramBotLink`. Изолированный PostgreSQL:
`node scripts/test-telegram-profile-link-db.mjs <путь к @electric-sql/pglite/dist/index.js>`.
Этот тест создаёт только временную in-memory базу, не подключается к Supabase.
Проверяются ownership, TTL, replay, запрет замены/конфликты, отмена, права и rollback
при сбое записи metadata. Живая доставка через Telegram проверяется отдельно после настройки.
