## 1. Доменный слой и архитектура

Цель: сделать доменную модель (бронирование, расписание, промо, финансы) ещё более независимой от Supabase/Next и удобной для повторного использования.

### 1.1. Выделение core-domain пакета

- [x] 🟠 **CORE-1**: Создать пакет `packages/core-domain`
  - Описать цель пакета в README (что сюда входит, а что нет)
  - Настроить экспорт через `index.ts` (booking, schedule, promotions, finance как модули)
  - Настроить сборку/типизацию как у `shared-client`

- [x] 🟠 **CORE-2**: Вынести доменные модели и сервисы бронирования
  - Описать `Booking`, `Branch`, `Staff`, `Service` как доменные типы (без привязки к Supabase типов)
  - Вынести в пакет `core-domain`:
    - валидацию параметров бронирования (`validateCreateBookingParams` и подобное)
    - работу с результатами RPC (`extractBookingId` и пр.)
  - Обновить API-роуты (`quick-hold`, `bookings/*`) на использование этих сервисов

- [x] 🟡 **CORE-3**: Оформить репозитории как интерфейсы
  - В `core-domain` ввести интерфейсы `BookingRepository`, `StaffRepository`, `BranchRepository`, `PromotionRepository`
  - В `apps/web` реализовать адаптеры поверх Supabase (RPC/таблицы)
  - Покрыть репозитории базовыми тестами (в т.ч. с использованием тестовой БД)

### 1.2. Application use-cases поверх домена

- [x] 🟡 **APP-1**: Ввести слой application use-cases
  - Для ключевых сценариев создать сервисы вида:
    - `CreateBookingUseCase`
    - `CancelBookingUseCase`
    - `ConfirmBookingUseCase`
    - `SendBookingNotificationsUseCase`
  - Вынести в них “оркестрацию”: вызовы домена + репозиториев + нотификаций

- [x] 🟡 **APP-2**: Упростить API-роуты до тонких адаптеров
  - Для нескольких ключевых эндпоинтов (например, `quick-hold`, `bookings/cancel`, `/api/notify`) переписать обработчики в виде:
    - HTTP → валидация (Zod) → вызов use-case → маппинг результата → HTTP-ответ
  - Зафиксировать паттерн в мини-гайде (HOWTO: новый API endpoint)
