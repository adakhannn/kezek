# Модель работы с датами

Статус: правило для нового кода и справочник общих helpers, сверка 2026-11-01. Соответствие всех существующих сценариев этому правилу не установлено; конкретные расхождения — [DATE_HANDLING_RISKS](DATE_HANDLING_RISKS.md).

## Дата и момент времени

| Тип | Примеры | Контракт |
| --- | --- | --- |
| Календарная дата | shift_date, valid_from, valid_to, день расписания | YYYY-MM-DD / SQL date; день в выбранном календаре без преобразования в UTC-полночь |
| Момент времени | start_at, end_at, opened_at, closed_at | ISO 8601 с Z или offset / SQL timestamptz; сравнение моментов отдельно от выбора календарного дня |

Дата 2026-11-01 и момент 2026-11-01T00:00:00Z — разные значения. Нельзя выбирать «сегодня» через UTC-срез, если операция относится к дню бизнеса в другой зоне.

## Helpers в текущем коде

Источник — [time.ts](../apps/web/src/lib/time.ts).

| Helper | Результат и граница |
| --- | --- |
| getTimezone() | NEXT_PUBLIC_TZ либо Asia/Bishkek; строка не проходит самостоятельную проверку timezone |
| getBusinessTimezone(businessTz) | Непустая обрезанная строка бизнеса либо getTimezone(); вызывающий код сам передаёт business.tz |
| todayDateString(tz), todayStringInTz(tz) | Строка текущей календарной даты в выбранной зоне |
| toDateString(date,tz), formatDateInTz(date,tz) | Строка календарной даты заданного момента |
| todayTz(tz) | **Date**, соответствующий началу текущего дня в зоне; не строка YYYY-MM-DD |
| dateAtTz(ymd,hhmm,tz) | Date для указанного локального дня и времени |
| addDaysToDateString, dateRangeInclusive | Строки дат/включительный диапазон; входы должны быть предварительно проверены |
| TZ | Значение getTimezone, вычисленное при загрузке модуля; его наличие не означает использование timezone конкретного бизнеса |

[toNormalizedDateString](../apps/web/src/lib/dateUtils.ts) возвращает первые 10 символов подходящей строки date/ISO либо null. Он не проверяет существование календарной даты или порядок valid_from/valid_to. Не называйте его строгим валидатором.

## Правила изменения сценария

1. Определить timezone операции: зона бизнеса, пользователя либо явно согласованная системная зона. Передать её по всей цепочке UI → HTTP → service → SQL.
2. Для календарной даты принимать проверенный YYYY-MM-DD; для момента требовать timezone/offset. Не исправлять невалидный ввод молчаливым усечением.
3. Вычислять «сегодня» в момент операции. Значение при загрузке модуля устаревает в долгоживущем процессе.
4. Для периода отдельно задать включительность. Удобная граница timestamp-выборки — начало первого дня включительно и начало следующего за последним дня исключительно; это правило нужно согласовать с конкретным SQL/API.
5. При отображении календарной даты не полагаться на timezone устройства после неявного преобразования date-only в Date. Для момента форматировать в явно выбранной зоне.
6. Проверять конец месяца/года, високосную дату, смену суток и различающиеся зоны клиента/бизнеса. Если поддерживаются зоны с переводом часов, включить их граничные дни.

Это требования к реализации и проверке, а не отчёт о выполненных тестах. Реальные входы и ошибки HTTP перечислены в [API](../API_DOCUMENTATION.md), финансовые расхождения — в [инженерном реестре](ENGINEERING_FINDINGS.md).
