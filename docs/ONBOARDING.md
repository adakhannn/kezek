# Первая задача разработчика

Статус: действующий маршрут чтения. Обновлено 30 октября 2026. Ответственная роль: сопровождающий документации и разработчик, принимающий задачу.

Этот маршрут помогает выбрать нужные документы для первой задачи. Установка описана в [руководстве запуска](../GETTING_STARTED.md), полный каталог — в [индексе документации](README.md).

## Что нужно выяснить

| Шаг | Прочитать | Результат |
| --- | --- | --- |
| 1. Уточнить задачу | [Состояние проекта](PROJECT_STATUS.md) и текущий запрос | Понятно, какой результат нужен и какая работа входит в задачу |
| 2. Найти цепочку кода | [Архитектура](../PROJECT_DOCUMENTATION.md) | Найдены клиент, API или прямой RPC, доменная логика и SQL, участвующие в выбранном сценарии |
| 3. Подготовить среду, если нужен запуск | [Настройка](../GETTING_STARTED.md) | Известны допустимый стенд, источник схемы, настройки и ограничения интеграций |
| 4. Выбрать способ изменения и проверки | [Правила разработки](../CONTRIBUTING.md), нужный раздел [проверок](../TESTING_GUIDE.md) | Определены затронутые слои, ожидаемое поведение и подходящие проверки |

Для документальной задачи шаг запуска не нужен. Для работы с закрытой WEB-кампанией дополнительно прочитать [её handoff](WEB_AGENT_HANDOFF.md); старые очереди и команды не возобновляют её.

Полный исходный набор схемы БД пока не восстановлен в репозитории. Поэтому обещание «клонировать и выполнить reset» не является рабочим путём новичка. Доступный вариант подготовки стенда должен быть определён до запуска.

## Перед первым изменением

- [ ] Сохранить исходные изменения рабочего дерева; не считать неизвестные правки своими.
- [ ] Найти реализацию выбранного сценария и документ, который нужно будет обновить.
- [ ] Записать ожидаемый результат и способ отличить исправление от частичного успеха.
- [ ] Для запуска определить среду и допустимые данные; для редактуры документов достаточно проверки ссылок и diff по CONTRIBUTING.

## Как оценивать доказательства

Исходники показывают реализованный контракт, отчёт проверки — наблюдение в конкретную дату и среде. Наличие теста или миграции не означает успешный прогон или применение на сервере. Факты WEB-приёмки находятся в [ledger](WEB_VERIFICATION_LEDGER.json), ограничения работы с ними — в handoff.

Читайте архив для конкретного исторического вопроса, после текущего справочника по теме.
