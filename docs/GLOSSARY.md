# Глоссарий Kezek

Статус: справочник терминов для продукта и разработки; сверено по исходникам **1 ноября 2026**. Сопровождение: продукт и разработка. Используется при чтении UI, кода и документации. Подробные правила — [функциональная модель](../SYSTEM_FEATURES_DOCUMENTATION.md), права и входы/ответы операций — [API-карта](../API_DOCUMENTATION.md).

Словарь объясняет назначение роли или сущности, но не подтверждает доступ пользователя. Его определяют проверки handler/service/RPC, контекст бизнеса и состояние БД. Документ не является результатом runtime- или RLS-проверки.

## Бизнес, пользователь и рабочая запись

| Термин | Значение |
| --- | --- |
| **Бизнес (business, biz)** | Организация в модели Kezek, объединяющая филиалы, услуги, сотрудников и настройки. Запись business не подтверждает юридический статус организации. В связях часто используется biz_id. |
| **Филиал (branch)** | Точка обслуживания конкретного бизнеса с адресом/координатами, расписанием и настройками. Основной филиал сотрудника может отличаться от места его работы в выбранный день. |
| **Пользователь (user)** | Идентичность аутентификации. Одна учётная запись может иметь несколько ролей и связей с бизнесами. |
| **Профиль (profile)** | Данные пользователя в profiles: имя, контакты и другие поля. Прочитанные сервисы ищут профиль по profiles.id = user.id; это не staff-запись. |
| **Сотрудник (staff)** | Рабочая запись с привязкой к бизнесу/филиалу, услугам, расписанию и финансовым параметрам. staff.user_id связывает её с учётной записью и может отсутствовать. Наличие профиля не означает наличие staff или права на staff-кабинет. |
| **Клиент (client)** | Участник посещения. У авторизованной записи client_id связывает бронь с пользователем; контакты гостя не создают такую связь автоматически. Слово client не является синонимом profiles или staff. |
| **Гостевая запись (guest booking)** | Бронирование по переданным имени/контактам без обязательной связи client_id. Совпадение имени/телефона само по себе не делает запись частью истории текущего аккаунта. |
| **Услуга (service)** | Предложение с длительностью, ценовыми полями и связями с филиалами/сотрудниками. Цена услуги, сумма позиции смены и реальный платёж — разные данные. |
| **Текущий бизнес (current business)** | Выбранный контекст для операций пользователя. Выбор бизнеса не выдаёт роль и не заменяет проверку доступа к объекту. |
| **Активность и одобрение** | is_active у сущности, is_approved у бизнеса и ограничения подачи заявок — разные состояния. Их нельзя свести к одному универсальному «бизнес заблокирован». |

Источники идентичности и контекста: [businessRoleApplicationService](../apps/web/src/lib/businessRoleApplicationService.ts), [staffRoleSync](../apps/web/src/lib/staffRoleSync.ts), [profileUpdateService](../apps/web/src/lib/profileUpdateService.ts), [BUSINESS_WORKFLOWS](api/BUSINESS_WORKFLOWS.md).

## Роли и кабинеты

Названия бизнесовых ролей взяты из [BUSINESS_ROLE_LABELS](../apps/web/src/lib/businessRoleApplicationService.ts); пользовательские названия кабинетов — из [RU-словаря header](../apps/web/src/app/_components/i18n/dictionaries/header.ru.ts).

| Ключ | Термин | Значение и граница |
| --- | --- | --- |
| super_admin | **Супер-администратор платформы** | Отдельная глобальная роль. Проверка admin layout ищет role_key=super_admin с biz_id IS NULL. Это не business admin и не доказательство одинакового обхода проверок во всех API. |
| owner | **Владелец** | Роль конкретного бизнеса. Отдельные сервисы также проверяют owner_id. Название не означает «все действия без ограничений». |
| admin | **Администратор** | Самостоятельная бизнесовая роль; отличается от super_admin и manager. |
| manager | **Менеджер** | Самостоятельный ключ бизнесовой роли. В коде manager-контекст часто объединяет разрешённые owner/admin/manager для конкретного сценария, но не делает эти назначения одинаковыми. |
| staff | **Сотрудник** | Ролевое назначение, отдельное от записи staff. Staff-контекст дополнительно связывает пользователя с активной рабочей записью. |
| client | **Клиент** | Пользовательский режим для личного кабинета и записей; условия владения записью проверяются отдельно. |

**Администратор филиала (branch admin)** — назначение к конкретному филиалу через отдельные API/RPC. Его не следует автоматически приравнивать к ключу admin на весь бизнес. Назначение и снятие описаны в [BUSINESS_WORKFLOWS](api/BUSINESS_WORKFLOWS.md).

**Кабинет** — область интерфейса, а не отдельная идентичность: `/admin` — «Админ-панель», `/dashboard` — «Кабинет бизнеса», `/staff` — «Кабинет сотрудника», `/cabinet` — «Личный кабинет» / «Мои записи». Переключатель кабинета показывает варианты навигации; видимость ссылки не доказывает доступ ко всем операциям раздела.

Проверки: [adminAccess](../apps/web/src/lib/adminAccess.ts), [authBiz](../apps/web/src/lib/authBiz.ts), [контракты администрирования](api/ADMIN_API.md) и [сотрудников/финансов](api/STAFF_AND_FINANCE.md).

## Бронирование и расписание

| Термин | Значение |
| --- | --- |
| **Бронь / бронирование (booking)** | Запись на посещение конкретного филиала и сотрудника в интервал времени. Основная сущность bookings; идентичность клиента, состав услуг и финансовый учёт — связанные, но отдельные данные. |
| **Комплекс услуг (service complex)** | Несколько услуг одного визита к одному сотруднику в одном филиале. Услуги выполняются последовательно, суммарная длительность учитывается при поиске времени. |
| **Состав бронирования (booking composition)** | Упорядоченные строки услуг в booking_services. Основное bookings.service_id само по себе не описывает весь комплекс и не гарантирует расчёт полной цены комплекса во всех путях. |
| **Слот (slot)** | Потенциальный интервал для записи, полученный из доступности. Чтение свободного слота не резервирует его. |
| **Удержание (hold)** | Временная резервирующая запись; срок и дальнейшие шаги зависят от вызова. Это не синоним confirmed. |
| **Расписание (schedule)** | Правила рабочих интервалов, перерывов и мест работы филиала/сотрудника. В исходниках сосуществуют legacy и explicit-модели. |
| **Недельный план / исключение дня** | В explicit-модели — обычные правила ISO-дней 1–7 и отдельное переопределение конкретной даты. Сброс дня возвращает недельный план через новую версию. |
| **Ревизия (revision)** | Версия расписания; expectedRevision позволяет обнаруживать устаревшего редактора в соответствующей операции публикации. Это не универсальная блокировка всех связанных записей. |
| **Отсутствие (absence)** | Период недоступности сотрудника. Сохранение может конфликтовать с существующими бронированиями. |
| **Рабочий филиал (work location)** | Филиал работы сотрудника на конкретный день; отличается от основного branch_id в staff. |

Пять значений [BookingStatus](../packages/core-domain/src/booking/types.ts):

| Статус | Значение |
| --- | --- |
| hold | Временное удержание |
| confirmed | Подтверждённая запись |
| paid | Финальная отметка посещения «пришёл/выполнено», используемая в учёте и применении скидок/пакетов; не подтверждение банковского платежа |
| cancelled | Отменённая запись |
| no_show | Клиент не пришёл |

Набор статусов не определяет сам по себе разрешённые переходы, авторизацию или поведение повторного запроса. Они описаны в [BOOKING_AND_CATALOG](api/BOOKING_AND_CATALOG.md). Модель расписания — [scheduling/model](../apps/web/src/lib/scheduling/model.ts), API — [BUSINESS_WORKFLOWS](api/BUSINESS_WORKFLOWS.md#расписания-и-отсутствия); продуктовый контекст комплекса — [SERVICE_COMPLEXES_FEATURE](SERVICE_COMPLEXES_FEATURE.md).

## Смены, суммы и расчёт

| Термин | Значение |
| --- | --- |
| **Смена (shift)** | Рабочая запись сотрудника за shift_date со статусом открытия/закрытия, временами и финансовыми полями; хранится в staff_shifts. Календарная дата и фактическая длительность — разные поля. |
| **Позиция смены (shift item)** | Сохранённая строка услуги/суммы/расходников в staff_shift_items, возможно связанная с booking. Число строк не обязательно равно числу уникальных клиентов или визитов. |
| **Ledger смены** | В этой документации — сохранённый набор позиций смены. Это не бухгалтерская двойная запись, банковский реестр или гарантированно неизменяемый журнал. |
| **Сумма услуг (totalAmount)** | Сумма услуг для расчёта; в общем finance-модуле расходники не вычитаются из неё перед расчётом процента. |
| **Расходники (totalConsumables)** | Отдельная сумма, включаемая в базовую долю бизнеса в общем модуле. Она не защищена от уменьшения доли бизнеса на доплату до гарантии. |
| **Проценты сотрудника/бизнеса** | Настройки распределения суммы услуг. Общий модуль нормализует корректную пару с положительной суммой; пограничные значения и округление описаны в функциональной модели. |
| **Базовая доля сотрудника (baseMasterShare)** | Процентная доля до применения гарантии. В calculateBaseShares округляется до целого. |
| **Базовая доля бизнеса (baseSalonShare)** | В calculateBaseShares — сумма услуг минус базовая доля сотрудника плюс расходники, с остатком округления в пользу бизнеса. |
| **Гарантия (guaranteedAmount)** | В действующем общем расчёте — часы × почасовая ставка при положительных значениях, с округлением до двух знаков. Это не отдельная фиксированная выплата или минимальная выручка бизнеса. |
| **Доплата (topupAmount)** | Положительная разница между гарантией и **базовой** долей сотрудника. Сравнивать с уже итоговой masterShare неправильно. |
| **Итоговая доля сотрудника (masterShare)** | Максимум базовой доли и гарантии в стандартном режиме. Рассчитанное начисление, а не подтверждённая выплата. |
| **Итоговая доля бизнеса (salonShare)** | Базовая доля за вычетом доплаты, ограниченная снизу нулём. Нулевой результат не объясняет, откуда финансируется гарантия сверх суммы услуг и расходников. |
| **Снимок расчёта (snapshot)** | Переданные или сохранённые суммы и параметры на определённый момент. Не означает неизменность: есть переоткрытие, корректировка часов и отчёты с пересчётом. |
| **Реальный платёж / выплата** | Факт движения денег, требующий собственного подтверждения. Нельзя выводить из paid, закрытой смены, выданного пакета или masterShare. |
| **Корректировка (adjustment)** | В core-domain есть утилита дельт serviceDelta/consumablesDelta. Она не равна реализованному журналу возвратов, отдельному refund API или банковскому возврату. |

Режимы [PaymentMode](../packages/core-domain/src/finance/modes.ts): percent_with_guarantee — стандартная ветка общего расчёта; percent_only — отдельная ветка без гарантии/доплаты. fixed_per_shift и custom присутствуют в типе как зарезервированные варианты, без собственной формулы в текущем calculateShiftFinancials. Наличие типа не подтверждает доступный пользователю переключатель.

Канонические формулы и примеры — [финансовая модель](../SYSTEM_FEATURES_DOCUMENTATION.md#3-смены-и-финансовая-модель), реализация — [core-domain/finance](../packages/core-domain/src/finance/index.ts). Не все отчёты и cron используют этот модуль. Контракты операций — [STAFF_AND_FINANCE](api/STAFF_AND_FINANCE.md), ограничения целостности — [ENGINEERING_FINDINGS](ENGINEERING_FINDINGS.md).

## Акции и пакеты визитов

| Термин | Значение |
| --- | --- |
| **Акция / промо (promotion)** | Предложение филиала с типом, активностью, периодом и параметрами. Типы: free_after_n_visits, referral_free, referral_discount_50, birthday_discount, first_visit_discount. Условия отличаются; наличие birthday_discount в enum не означает работающую проверку дня рождения. |
| **Применение промо (promotion application)** | Выбор применимой акции и расчёт скидки для конкретной записи в соответствующей SQL-цепочке. Требует условий реализации; не синоним полученного платежа. |
| **Использование промо (promotion usage)** | Запись client_promotion_usage о применении. Её наличие не доказывает общую идемпотентность всех вызывающих путей. |
| **Реферальный бонус** | Право на бонус, описанное связью client_referrals и bonus_used. Нельзя добавлять условие «друг точно оплатил» без проверки соответствующего пути создания/проверки связи. |
| **План пакета (visit package plan)** | Шаблон visit_package_plans: число визитов, срок, скидка и ограничения применимости. План отдельно от конкретного пакета клиента. |
| **Клиентский пакет (client visit package)** | Запись client_visit_packages, выданная пользователю по плану. Endpoint продажи создаёт запись пакета; сам по себе не проводит платёж и не доказывает его получение. |
| **Остаток визитов (remaining visits)** | Количество доступных использований пакета. При успешном применении соответствующая функция уменьшает его на один и пишет использование. Без успешного применения сам статус paid не гарантирует списание. |
| **Использование пакета / subscription_applied** | Связь применения пакета с booking. В рассматриваемой SQL-цепочке пакет проверяется перед промо; это не гарантия изоляции бизнеса или отсутствия повторов во всех операциях. |

Условия, цены, приоритет и ограничение гостевых броней без client_id — [функциональная модель](../SYSTEM_FEATURES_DOCUMENTATION.md#4-промоакции-и-пакеты-визитов). API — [акции](api/STAFF_AND_FINANCE.md#акции-филиала) и [пакеты](api/BUSINESS_WORKFLOWS.md#планы-и-клиентские-пакеты-визитов). Открытые риски не становятся закрытыми из-за терминов «пакет» или «автоматическое применение»; см. [ENGINEERING_FINDINGS](ENGINEERING_FINDINGS.md).

## Рейтинги, метрики и качество

| Термин | Значение |
| --- | --- |
| **Дневной рейтинг (day score)** | Расчёт из компонент качества, продуктивности, лояльности и дисциплины за день. Веса и формулы — модель продукта, не объективная оценка человека. |
| **Агрегированный рейтинг** | Результат по окну дневных показателей с fallback при отсутствии данных. NULL означает отсутствие значения; 0 — числовой результат; 50 может быть fallback, а не наблюдённая оценка. |
| **Агрегат** | Подготовленная сводка исходных данных. Наличие таблицы/cron не доказывает, что сводка полна или пересчитана после последнего изменения. |
| **API-метрики** | Данные о запросах, для которых включён соответствующий сбор: метод, путь, статус, длительность и контекст. Таблица api_request_metrics не гарантирует охват каждого endpoint. |
| **Событие воронки (funnel event)** | Событие этапа взаимодействия, переданное в funnel_events. Схема допускает session_id, идентификаторы и metadata; автоматическую анонимность утверждать нельзя. |
| **Frontend-метрика** | Данные о загрузке, рендере или Web Vitals. Сохранение может запускаться без ожидания; HTTP-успех не доказывает наличие строки. |
| **Core Web Vitals** | Показатели пользовательского опыта, для которых проект имеет сбор метрик. Наличие сборщика не доказывает достижения целевых значений. |
| **Smoke-проверка** | Ограниченная проверка запуска/основных сценариев. Не заменяет полную функциональную, ролевую или нагрузочную проверку. |
| **E2E-проверка** | Выполнение сквозного пользовательского сценария. Наличие Playwright-теста или его исходника не означает выполненный и успешный прогон. |
| **Статическая сверка (source review)** | Чтение route, сервисов, схем, типов и SQL без исполнения продукта. Подтверждает наблюдённую структуру исходников, не состояние deployed DB или runtime-результат. |
| **Приёмка / evidence** | Зафиксированный результат проверки в определённой среде и дате. Исторический PASS не переносится автоматически на новый код, роль или окружение. |

Рейтинговые правила — [функциональная модель](../SYSTEM_FEATURES_DOCUMENTATION.md#5-рейтинги-и-аналитика). Контракты телеметрии — [OPERATIONS_AND_TELEMETRY](api/OPERATIONS_AND_TELEMETRY.md); источники — [funnelEventsService](../apps/web/src/lib/funnelEventsService.ts), [frontendMetricsService](../apps/web/src/lib/frontendMetricsService.ts). Правила проверки — [TESTING_GUIDE](../TESTING_GUIDE.md), состояние закрытой WEB-кампании и навигация по её фактам — [WEB_AGENT_HANDOFF](WEB_AGENT_HANDOFF.md).
