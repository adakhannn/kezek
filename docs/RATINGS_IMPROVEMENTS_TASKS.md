## Улучшения системы рейтингов

Этот документ описывает план по развитию и укреплению системы рейтингов (сотрудники, филиалы, бизнесы).

### 1. Конфигурация и архитектура

- **1.1. Локальные конфиги рейтинга (per‑biz / per‑категория) ✅**  
  - **Задачи:**
    - Спроектировать `rating_biz_config` (или аналог) с возможностью переопределять глобальные веса и окно `window_days` для конкретного бизнеса или категории.
    - Определить стратегию наследования: глобальный конфиг → категорийный → конфиг бизнеса.
    - Обновить сервисный слой расчёта рейтингов так, чтобы он выбирал “актуальную” конфигурацию по бизнесу.
    - Добавить simple‑UI для просмотра/редактирования конфигов на уровне бизнеса (минимум read‑only просмотр в дашборде владельца).

- **1.2. История рейтингов и метаданные пересчёта ✅**  
  - **Задачи:**
    - Добавить поля `last_rating_recalculated_at` для `staff`, `branches`, `businesses` (или отдельную history‑таблицу).
    - Обновить RPC пересчёта рейтингов так, чтобы он заполнял эти поля.
    - В админ‑UI (`ratings-status`, `ratings-debug`) отображать дату последнего успешного пересчёта по сущности/уровню.

### 2. Cron и пайплайн пересчёта

- **2.1. Догоняющий пересчёт пропущенных дней ✅**  
  - **Задачи:**
    - Внутри `recalculate_ratings_for_date` (или нового RPC) добавить режим “интервал дат”, а не только одна дата.
    - Либо в `/api/cron/recalculate-ratings`:
      - определять последние N дней без метрик по `*_day_metrics`,
      - последовательно вызывать RPC для каждого дня в окне (с ограничением по количеству).
    - Обновить логирование, чтобы было видно, сколько именно дней и сущностей пересчитано.

- **2.2. Более богатый health‑check cron‑задачи ✅**  
  - **Задачи:**
    - В логах cron (`RecalculateRatingsCron`) дополнительно считать и логировать:
      - долю сущностей с `rating_score IS NULL` по каждому уровню;
      - количество ошибок из `rating_recalc_errors` за день.
    - При критических отклонениях (например, > 10% сущностей без рейтинга или есть ошибки) включать более жёсткий alert (отдельный тип письма / повышенный приоритет).

### 3. Формула рейтинга и бизнес‑логика

- **3.1. Порог “достаточно данных для рейтинга” ✅**  
  - **Задачи:**
    - Ввести минимальный объём данных (например, `min_clients`, `min_shifts`) для расчёта стабильного рейтинга.
    - Если порог не достигнут:
      - либо не выставлять числовой рейтинг (`rating_score = NULL` и показывать “недостаточно данных”),
      - либо сильнее сглаживать значение (отдельный режим внутри формулы).
    - Добавить эти правила в документацию и подсказки UI.

- **3.2. Расширение компонента “дисциплина” ✅**  
  - **Задачи:**
    - Проанализировать доступные сигналы дисциплины (no‑show, отмены, закрытие смены, пропуски).
    - Спроектировать, как они влияют на дисциплинарный под‑скор (штрафы/бонусы).
    - Обновить расчёт дисциплины в сервисном слое и документации.

### 4. Админ‑инструменты и UX

- **4.1. Улучшение `/admin/ratings-status` ✅**  
  - **Задачи:**
    - Добавить в API `/api/admin/ratings/status` агрегаты по ошибкам:
      - количество строк в `rating_recalc_errors` за последние N дней;
      - флаг `has_recent_errors`.
    - На странице `ratings-status` отобразить эти значения и визуальный индикатор (“есть ошибки пересчёта за последние N дней”).

- **4.2. Расширение `/admin/ratings-debug` ✅**  
  - **Задачи:**
    - Добавить в debug‑API возможность точечного пересчёта:
      - по конкретному `staff_id` / `branch_id` / `biz_id` и дате/интервалу.
    - В UI рядом с каждой проблемной сущностью показать кнопку “Пересчитать рейтинг” или “Пересчитать метрики за период” (с подтверждением).
    - Логировать такие ручные перезапуски (кто, когда, что именно пересчитал).

- **4.3. Фоновая job‑система для массового пересчёта ✅**  
  - **Задачи:**
    - Создать таблицу `rating_jobs` (id, инициатор, диапазон дат, статус, прогресс, ошибки).
    - Перевести `initialize_all_ratings` на модель “записали job → фоновой воркер обрабатывает”, вместо долгого синхронного вызова RPC.
    - В админке добавить экран/блок “Активные и завершённые задачи пересчёта рейтингов”.

### 5. Документация и прозрачность

- **5.1. Описание формулы рейтинга для пользователей ✅**  
  - **Задачи:**
    - Создать отдельный docs‑раздел “Как считается рейтинг” (ориентирован на владельцев/менеджеров).
    - Кратко описать компоненты рейтинга, веса, окно дней и пороги “достаточно данных”.
    - Добавить ссылку на этот документ в UI (например, рядом с рейтингом или в справке кабинета).

### 6. Первая итерация реализации (MVP‑улучшения)

Первая итерация фокусируется на улучшении наблюдаемости и снижении рисков “тихих” поломок:

- **6.1. Расширить `/api/admin/ratings/status` и UI `ratings-status` ✅**  
  - Вернуть из API агрегированную информацию по `rating_recalc_errors` (за последние N дней) и использовать её в интерфейсе.

- **6.2. Улучшить логирование cron `/api/cron/recalculate-ratings` ✅**  
  - Включить в логи долю сущностей без рейтинга и количество ошибок за день, чтобы можно было быстрее находить деградации.
