# Service client и граница бизнеса

Статус: правила нового и изменяемого кода, уточнены по helpers 1 ноября 2026. Это не свидетельство соответствия всех существующих запросов. Открытые отклонения — [инженерный реестр](ENGINEERING_FINDINGS.md).

## Выбор клиента и контекста

Привилегированный клиент может обходить RLS. Его использование требует проверки вызывающего, разрешённой операции и границ каждого объекта. Наличие бизнес-фильтра без проверки пользователя недостаточно.

Для cookie-based кабинета бизнеса стандартная обёртка — [withManagerContext](../apps/web/src/lib/withManagerContext.ts): она получает [управленческий контекст](../apps/web/src/lib/authBiz.ts) и передаёт supabase, admin, bizId и userId. Это правило выбора существующего helper, не универсальный Bearer wrapper. Mobile и смешанные API должны явно разрешать поддерживаемый способ identity; параметры Request сами не добавляют Bearer-поддержку.

[withManagerAndStaffContext](../apps/web/src/lib/withManagerAndStaffContext.ts) дополнительно проверяет выбранного сотрудника. Он не проверяет автоматически все IDs в body. Для нового обработчика использовать [общую цепочку](../apps/web/src/lib/HOWTO_NEW_API_ENDPOINT.md).

## Инварианты операции

1. Получить identity и разрешённый бизнес из доверенной проверки.
2. Для каждой сущности проверить принадлежность этому бизнесу; для дочерних ID проверить связь с целевым объектом.
3. В привилегированном запросе ограничить выборку/мутацию проверенными IDs и бизнесом там, где это поле существует.
4. При вставке сервер назначает biz_id из разрешённого контекста. Для административного выбора чужого бизнеса отдельно проверяется полномочие платформы.
5. Выполнять проверки до мутаций; для связанного изменения определить транзакцию или контроль ревизии, повторы и частичный отказ.
6. Проверять Supabase error и количество затронутых строк. Успешный Promise без исключения не доказывает изменение.

[authCheck](../apps/web/src/lib/authCheck.ts) возвращает результат проверки принадлежности. Он не фильтрует последующие запросы вызывающего кода и не защищает от изменения состояния между проверкой и записью.

## Администрирование, cron и публичные операции

- Platform admin требует собственной проверки super-admin identity; manager context на один бизнес ей не равнозначен.
- Cron требует аутентификации задания и ограниченного состава операций; отсутствие user session само по себе не разрешает service role.
- Публичный endpoint нуждается в явно заданной публичной модели данных и ограничениях злоупотребления. Service key нельзя помещать в клиент.
- SECURITY DEFINER RPC проверяются отдельно по правам EXECUTE, владельцу и проверкам внутри SQL.

Текущие реализации этих потоков различаются: [API](../API_DOCUMENTATION.md), [cron](../CRON_SETUP.md), [архитектура](../PROJECT_DOCUMENTATION.md). В частности, ENG-02/03 показывают, почему проверка только внешнего объекта недостаточна.

## Проверка изменения

Нужны случаи чужого бизнеса, вложенного чужого ID, отсутствующей identity, недопустимой роли и отказа посередине записи. Метод и среду выбирать по [CONTRIBUTING](../CONTRIBUTING.md); результаты не заменять чтением helper. Исторический [аудит](SERVICE_CLIENT_AND_BIZ_FILTERS_AUDIT.md) служит источником прежних наблюдений, не текущим полным списком использования.
