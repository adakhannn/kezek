# Оптимизация производительности раздела «Финансы»

Документ описывает план поиска причин долгой загрузки `/dashboard/staff/[id]/finance` и оптимизации API `/api/staff/finance` и связанных endpoинтов.

## 1. Диагностика (что и как измеряем)

- **1.1. Включить детальное логирование для `/api/staff/finance` (P0)**
  - [x] В `apps/web/src/app/api/staff/finance/route.ts` добавить лог `logDebug('StaffFinance', 'Timing', { ... })` с:
    - общей продолжительностью запроса;
    - параметрами `staffId`, `date`;
    - признаком, что использовался `useServiceClient`.
  - [x] Убедиться, что `logApiMetric` корректно пишет длительность в таблицу метрик и что можно фильтровать по endpoint = `/api/staff/finance`.

- **1.2. Замерить время работы подзапросов в `getShiftData` (P0)**
  - [x] В `apps/web/src/app/staff/finance/services/shiftDataService.ts` обернуть каждый крупный запрос (staff, shift+items, bookings, services, day-off / schedule, allShifts) во вспомогательную обёртку, которая:
    - перед выполнением сохраняет `const t0 = Date.now()`;
    - после выполнения логирует `logDebug('ShiftDataService', 'Query timing', { part: 'bookings', durationMs: Date.now() - t0, staffId, ymd });`.
  - [ ] По логам понять, какой именно блок даёт основную задержку (часто это `bookings` или `staff_shifts` без индексов / с тяжёлыми RLS).

- **1.3. Проверить план выполнения (EXPLAIN ANALYZE) для медленных запросов (P1)**
  - [ ] В Supabase-консоли выполнить `EXPLAIN (ANALYZE, BUFFERS)` для:
    - выборки смены по `staff_id + shift_date` (как в `getShiftData`);
    - выборки `bookings` по `staff_id + start_at` за день.
  - [ ] Зафиксировать в этом документе «бутылочные горлышки» (seq scan по большим таблицам, фильтры по JSON, отсутствие подходящих индексов, тяжёлые RLS-политики).

- **1.4. Проверить поведение на клиенте (повторы, таймауты) (P1)**
  - [ ] В DevTools (Network) и логах фронта убедиться, что:
    - `useFinanceData` делает ровно один запрос к `/api/staff/finance` при открытии страницы или смене даты;
    - нет скрытых дополнительных ретраев (React Query / `fetchWithRetry`) сверх одной попытки;
    - таймаут (AbortError) корректно отображается пользователю как понятная ошибка.

## 2. Оптимизация бэкенда и БД

- **2.1. Индексы для основных запросов (P0 — уже частично сделано)**
  - [x] `staff_shifts(staff_id, shift_date)` — миграция `20260312110000_add_finance_indexes.sql`.
  - [x] `bookings(staff_id, start_at)` — та же миграция.
  - [ ] После включения логов из 1.2/1.3 проверить, нет ли дополнительных seq scan’ов по:
    - `service_staff(staff_id, is_active)` / `working_hours(staff_id, day_of_week)` / `staff_schedule_rules(staff_id, date_on)`;
    - при необходимости — добавить целевые индексы.

- **2.2. Упрощение и разбиение тяжёлых запросов (P1)**
  - [ ] Если `bookings` за день возвращает очень много строк:
    - рассмотреть ограничение по статусам (например, исключать уже «далёкое прошлое» или ненужные статусы);
    - вынести агрегации/соединения по услугам (`booking_services`) в отдельный запрос / материализованный view.
  - [ ] Для `allShifts`:
    - убедиться, что выборка ограничена разумным периодом (например, последний год), а не всей историей сотрудника;
    - при необходимости добавить LIMIT + пагинацию для статистики.

- **2.3. Анализ и оптимизация RLS / функций (P1)**
  - [ ] Проверить, не тянут ли RLS-политики на `staff_shifts`, `bookings`, `staff_time_off`, `working_hours`, `staff_schedule_rules` дополнительные подзапросы.
  - [ ] Для сценария владельца/менеджера убедиться, что:
    - используется `service client` там, где это безопасно и нужно для обхода тяжёлых RLS;
    - нет дублирующих проверок принадлежности к бизнесу.

## 3. Оптимизация клиентской логики

- **3.1. Управление повторами и таймаутами (P1)**
  - [ ] Перепроверить настройки `fetchWithRetry` для финансов:
    - `/api/staff/finance` — 0 ретраев + явный таймаут (уже реализовано в `useFinanceData`) → зафиксировать поведение как стандарт.
    - `/api/staff/shift/items` (автосейв, add/delete) — максимум 1 retry с короткими задержками.
  - [ ] При ошибке (500 или таймаут) показывать короткое, но информативное сообщение с CTA «Повторить».

- **3.2. Минимизация лишних запросов (P1)**
  - [ ] Убедиться, что SSR‑prefetch (`initialData` через `getShiftData` в `dashboard/staff/[id]/finance/page.tsx`) действительно отключает первый клиентский запрос для «сегодня».
  - [ ] Для навигации по датам:
    - кешировать результаты последнего запроса по дате (React Query уже делает это, но важно не сбрасывать кэш слишком агрессивно);
    - при возврате к недавно открытой дате — сразу показывать кэш и фоновый refetch.

## 4. Конкретные шаги «после диагностики»

После выполнения блока 1 (и частично 2.1) ожидается, что будет понятно, какой именно участок даёт задержку. В зависимости от результата:

- **Если медленен запрос к `staff_shifts`**:
  - Проверить план по новому индексу `staff_id + shift_date`.
  - При необходимости упростить выборку (убрать лишние поля, join’ы, лишние фильтры).

- **Если медленен запрос к `bookings`**:
  - Оптимизировать фильтры/индексы, ограничить диапазон дат, упростить join с услугами.

- **Если суммарно тормозит группа day-off / schedule / allShifts**:
  - Подумать о кешировании этих данных (например, `frontend_metrics` / отдельная таблица агрегатов).
