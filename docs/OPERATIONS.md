## Нагрузочный тест (локально)

R25-28: нагрузка не измерялась. Скрипты в [scripts/load](../scripts/load/run.mjs) задают воспроизводимый прогон **только против локального стека**: локальный Supabase из `supabase/` с fixture [e2e-seed](../scripts/e2e-seed.mjs) и локальный web. Статус результатов: **не измерено — нужен запуск с Docker** (28.11.2026 Docker daemon на машине агента не был запущен; проверены только guard, runner и формат отчёта на локальном stub-сервере).

**Почему никогда не против prod.** Прогон создаёт сотни записей и шлёт тысячи запросов в минуту: в production это реальные слоты салонов, уведомления клиентам и мастерам через outbox, расход квот Vercel/Supabase/Upstash и срабатывание limiter для настоящих пользователей Оша за общим NAT. Результат на shared prod-ресурсах к тому же нельзя повторить и отделить от живого трафика. Поэтому [guard](../scripts/load/guard.mjs) пропускает только `localhost`, `127.0.0.1` и `::1` (http/https, без credentials), отдельно отказывает `*.vercel.app`, `*.supabase.co`, `kezek.kg` и ref production-проекта, ходит с `redirect: 'manual'` и не имеет флага отключения; при отказе процесс завершается с кодом 2 до первого запроса. Нагрузочный прогон на staging/prod требует отдельного решения владельца, отдельной среды и плана.

**Как запустить** (из корня, Docker запущен; порты — из `supabase/config.toml`):

```bash
pnpm db:start:check                                     # локальный Supabase, как в CI
node scripts/e2e-seed.mjs > apps/web/e2e/.e2e.env       # бизнес e2e-salon, 2 мастера, услуги
# отдельный терминал: web c отдельным лимитом на каждый адрес клиента
(cd apps/web && set -a && . e2e/.e2e.env && set +a && \
  RATE_LIMIT_TRUSTED_IP_HEADER=x-forwarded-for pnpm dev --port 3100)
node scripts/load/run.mjs --base-url http://localhost:3100          # все сценарии, 10 → 50 → 100 VU по 20 с
node --test scripts/load/load.test.mjs                               # самопроверка без Docker (stub-сервер)
pnpm exec supabase stop --no-backup                                  # по завершении
```

Полезные опции: `--scenarios home,catalogue,business,slots,booking`, `--stages 10,50,100`, `--stage-seconds 60`, `--days 30`, `--seed-env <файл>`, `--dry-run` (проверить цели без запросов), `--cleanup-only <runId>`, `--help`. Сводка пишется в `scripts/load/results/load-<runId>.md` и `.json` (каталог в `.gitignore`) и печатается в stdout.

- **Лимитер.** `/api/quick-book-guest` защищён пресетом `public` (10 запросов в минуту на адрес). Без `RATE_LIMIT_TRUSTED_IP_HEADER` dev-сервер считает всех клиентов одним адресом `development-local`, и сценарий записи упрётся в 429; скрипт ставит каждому запросу свой `X-Forwarded-For` из `10.0.0.0/8`, поэтому переменную нужно задать именно для локального web. Память dev-limiter ограничена 10 000 ключей в окне — выше ~160 записей/с ответы станут 503 limiter (отчёт пометит это отдельно). `next start` без Upstash отвечает API-маршрутам 503 (fail-closed), поэтому запись меряется под `next dev`; страницы можно дополнительно измерить на production-сборке с тем же env: `pnpm -C apps/web build`, `pnpm -C apps/web exec next start --port 3200`, `--scenarios home,catalogue,business,slots --base-url http://localhost:3200`. Числа `next dev` — верхняя граница задержки, не прогноз для Vercel.
- **Тестовые данные и очистка.** Записи создаются гостем с именем `LOADTEST <runId>` и случайным номером `+99670xxxxxxx` в бизнесе fixture. После каждой ступени записи скрипт через `docker exec supabase_db_<project_id> psql` (как e2e-seed) проверяет пересечения и **отменяет** (не удаляет) записи прогона; `--no-cleanup` оставляет их, `--cleanup-only <runId>` отменяет позже. Полный сброс — `supabase db reset` + seed. Провайдеры уведомлений в локальном env не задаются, реальных отправок нет.

**Что измеряется.** Закрытая модель: N виртуальных пользователей без пауз, каждый сценарий проходит каждую ступень отдельно (после 3 неучтённых прогревочных запросов для страниц). На ячейку «сценарий × ступень»: число запросов, throughput (RPS), задержка p50/p95/p99/max (полное тело ответа, таймаут 30 с), доля ошибок (4xx/5xx, сетевые ошибки и таймауты; 429/503 limiter — отдельной колонкой), ожидаемые конфликты 409 «слот занят» — отдельно и не как ошибки, распределение кодов. После сценария записи — число созданных записей и **число пересечений активных записей одного мастера** (должно быть 0: двойная запись под конкуренцией — дефект целостности, а не производительности).

| Сценарий | Что вызывается |
| --- | --- |
| Главная | `GET /` |
| Каталог (поиск) | `GET /?q=E2E` (поиск и список бизнесов главной) |
| Страница бизнеса | `GET /b/e2e-salon` (SSR публичной страницы) |
| Свободные слоты | `POST /rest/v1/rpc/get_free_slots_service_day_v2` локального PostgREST с anon key — тот же RPC, что `useSlotsLoader` (`apps/web/src/app/b/[slug]/hooks/`) вызывает на шаге выбора времени для конкретного мастера; день — случайный из ближайших `--days` по `Asia/Bishkek` |
| Создание записи | `POST /api/quick-book-guest` (гостевая запись, сервисная команда создания подтверждённой записи) на слот из пула свободных слотов того же RPC; `Idempotency-Key` и `X-Booking-Client-Token` на каждый запрос |

Не входит: вход и кабинеты (нужны сессии), авторизованный `/api/quick-hold`, пагинированный RPC «любой мастер» (`get_free_slots_page_v1`), мобильное приложение, cron и outbox worker, смешанный профиль трафика. Это следующий шаг после первого измерения.

**Предлагаемые цели (SLO) для масштаба Оша.** Оценка: десятки салонов, в пик — единицы-десятки одновременных клиентов. 50 VU без пауз создают нагрузку намного выше такого пика, поэтому SLO проверяется на ступенях до 50 VU, а 100 VU — стресс-ступень для поиска «колена» (только наблюдение). Цели относятся к локальному стенду и являются предложением до решения владельца; для Vercel/Supabase prod они не доказаны.

| Сценарий | p95 при ≤ 50 VU | Ошибки | Прочее |

| Свободные слоты (RPC) | ≤ 300 мс | < 1 % | — |
| Создание записи | ≤ 1500 мс | < 1 % (без 409) | 0 пересечений записей одного мастера |

## User lifecycle ENG-31

Для сопровождающего, применяющего согласованный release; источник — [контракт](api/ADMIN_API.md#блокировка-и-удаление-пользователей-eng-31) и [миграция](../supabase/migrations/20261111090000_user_lifecycle.sql). Локальные проверки не означают применения к Supabase.

1. Сначала сверить историю миграций и сделать backup; существующий baseline и aliases описаны в [инструкции миграций](../supabase/APPLY_MIGRATIONS.md). Применить предшествующие зависимости и ENG-31 до переключения web handlers. Старый handler с разрушительной предварительной очисткой нельзя оставлять активным во время rollout: нужна пауза административных lifecycle-операций до обновления обеих сторон.
2. Проверить существующий PostgREST pre-request hook, включая role/database settings и config/env deployment. Миграция отказывается перетирать другой SQL hook; объединение с существующим hook требует отдельного явного изменения. Убедиться, что конфигурация сервиса не перекрывает `public.check_user_lifecycle_request`. Для будущих RLS-таблиц public/storage добавлять restrictive `user_lifecycle_access_allowed()`.
3. Проверить права владельца функций/триггеров в Auth и работу Auth после миграции. Локальный интеграционный runner использует GoTrue v2.180.0, PostgREST v13.0.7 и synthetic PostgreSQL 17; фактическая копия схемы/данных проверяется отдельно на Supabase PostgreSQL 17.6. Обновление managed Auth требует повторения lifecycle-контрактов: порядок app_metadata/ban и схема sessions являются проверяемой зависимостью.
4. В разрешённом staging подтвердить block → отказ старого access/refresh token и нового входа → unblock → новый вход; delete → сохранность истории. Реальные Storage/Realtime соединения и конкретный remote deployment требуют отдельной проверки. Уже выданный публичный URL, загруженные данные и ранее авторизованный запрос не отзываются этим протоколом.
5. При 503 повторить **то же действие с тем же reason**. Receipt определяет завершение, даже если ответ Auth потерян. Противоположное действие при pending даёт 409. Не удалять pending row и не переключать состояние вручную: запоздавший запрос ещё может исполняться. При постоянном FK/Auth отказе исправить установленную причину, затем повторить команду. Если прежний actor потерял роль, тот же повтор может выполнить другой действующий SA.

Прямые dashboard/API ban/delete без lifecycle-команды теперь намеренно отклоняются триггером; административный путь — обновлённые handlers. Service-only завершение due self-deletion сохраняется по собственной проверенной заявке. Нет автоматического восстановления ролей/связей, потерянных старой реализацией; такое восстановление требует отдельного подтверждённого источника.
