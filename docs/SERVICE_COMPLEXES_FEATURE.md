# Комплексы услуг (запись на несколько услуг за один визит) — описание фичи и план реализации

Документ описывает фичу **комплексов услуг**: возможность записаться на несколько услуг за один визит (один мастер, один филиал, услуги идут подряд). Приводятся выбранный вариант дизайна, границы фичи, модель данных и пошаговый список задач для реализации.

**Связанные документы:**  
`SYSTEM_FEATURES_DOCUMENTATION.md` (бронирование, слоты, промо), `docs/SUBSCRIPTIONS_AND_PACKAGES_FEATURE.md` (пакеты визитов), `docs/GLOSSARY.md` (термины).

---

## 1. Выбранный вариант

Принят вариант: **один визит = одно бронирование с несколькими услугами, один мастер, один филиал, услуги выполняются последовательно без разрывов.**

- Клиент в публичном визарде выбирает **несколько услуг** (мультиселект на шаге 4).
- Все услуги выполняет **один выбранный мастер** в **одном филиале**.
- Длительность визита = сумма длительностей выбранных услуг; слот в календаре — один непрерывный интервал.
- В БД создаётся **одна запись в `bookings`** и связанные строки в новой таблице **`booking_services`** (состав услуг).
- Обратная совместимость: существующий сценарий «одна услуга» остаётся; старые API и RPC продолжают работать, новые поля/таблицы расширяют модель.

**Почему этот вариант:**
- Минимальные изменения в логике слотов (достаточно считать слоты по суммарной длительности).
- Один визит = один `booking_id` — не ломаем аналитику, отчёты и промо/пакеты визитов.
- Позволяет позже ввести «фиксированные комплексы» (предустановленные наборы услуг) как надстройку над той же моделью.

## 2. Описание фичи

### 2.1 Назначение

Дать клиенту возможность при записи выбрать **несколько услуг за один визит** (например: стрижка + борода + укладка). Система показывает слоты с учётом суммарной длительности, создаёт одно бронирование с перечнем услуг; в кабинетах и отчётах визит отображается как один приход с несколькими позициями.

**Цели:**
- Удобство для клиента: одна запись вместо нескольких.
- Соответствие реальной практике салонов (комплексы «стрижка + мытьё», «маникюр + покрытие» и т.п.).
- Сохранение единой модели визита для финансов, промо и абонементов.

### 2.2 Кто пользуется

| Роль | Действия |
|------|----------|
| **Клиент (публичная запись)** | На шаге «Услуга» выбирает одну или несколько услуг; видит суммарную длительность и ориентир по цене; выбирает один слот под весь комплекс; получает одну запись. |
| **Владелец / Админ / Менеджер** | В календаре и отчётах видят запись как один визит с перечнем услуг; при необходимости редактирование/отмена как одного бронирования. |
| **Сотрудник (мастер)** | В своём расписании видит один блок на суммарное время с указанием списка услуг. |

### 2.3 Границы фичи

- **В рамках фичи (этап 1):**
  - Публичный визард: мультиселект услуг (шаг 4), слоты по суммарной длительности, создание одного бронирования с несколькими услугами.
  - Один мастер на весь комплекс; один филиал; услуги идут подряд (один временной интервал).
  - Отображение в кабинете клиента и в дашборде/календаре: одна карточка визита с перечнем услуг и общей длительностью/ценой.

- **Взаимодействие с существующими фичами:**
  - **Промо и пакеты визитов:** применяются к бронированию как к одному визиту; правила (по услуге, по филиалу) проверяются по составу бронирования (например, по первой услуге или по всем — см. раздел 4).
  - **Аналитика и воронки:** один визит = одно событие; в события можно добавить `service_ids[]` и `services_count` для детализации.

- **Вне скоупа на первом этапе:**
  - Разные мастера на разные услуги в одном визите (мультиресурсное расписание).
  - Предустановленные «каталог комплексов» (отдельный тип услуги-bundle) — можно добавить позже поверх той же модели `booking_services`.

### 2.4 Ключевые сценарии

1. **Клиент записывается на комплекс:** выбирает филиал → день → мастера → несколько услуг (например, «Стрижка», «Мытьё головы») → видит слоты по 1 ч 15 мин → выбирает слот → одна запись создаётся с двумя услугами.
2. **Клиент записывается на одну услугу:** поведение как сейчас — одна услуга в мультиселекте; слоты и создание бронирования работают в существующем режиме (обратная совместимость).
3. **Просмотр в кабинете:** клиент видит запись «10.03.2026, 14:00 — Стрижка, Мытьё головы — 1 ч 15 мин».
4. **Дашборд/календарь:** запись отображается одним блоком с тултипом/раскрытием списка услуг.

## 3. Модель данных

### 3.1 Концепция

- **Бронирование (`bookings`):** по-прежнему одна строка на визит. Добавляется связь «один ко многим» с составом услуг.
- **Состав услуг визита:** новая таблица `booking_services` — для каждого бронирования список услуг с порядком, длительностью и (при необходимости) ценой. Длительность визита и границы слота определяются суммой этих длительностей.
- **Обратная совместимость:** в `bookings` остаётся поле `service_id` (первая/основная услуга); все существующие RPC и API, работающие с одним `service_id`, продолжают использоваться для старых записей и для режима «одна услуга».

### 3.2 Схема БД

**Таблица `booking_services` (новая):**

| Колонка | Тип | Описание |
|---------|-----|----------|
| id | uuid PK DEFAULT gen_random_uuid() | |
| booking_id | uuid NOT NULL FK → bookings(id) ON DELETE CASCADE | |
| service_id | uuid NOT NULL FK → services(id) ON DELETE RESTRICT | |
| duration_min | integer NOT NULL | Длительность данной позиции (дублируем из services на момент записи) |
| order_index | integer NOT NULL DEFAULT 0 | Порядок выполнения (0, 1, 2, …) |
| price_from | numeric(10,2) | Опционально: цена «от» на момент записи |
| price_to | numeric(10,2) | Опционально: цена «до» на момент записи |
| created_at | timestamptz NOT NULL DEFAULT now() | |

**Индексы:** `booking_id` (для выборки состава по бронированию), `(booking_id, order_index)` для упорядоченного списка.

**Таблица `bookings` (без удаления существующих колонок):**

- `service_id` — сохраняем; для бронирований с несколькими услугами заполняем первой услугой (order_index = 0) для совместимости со старыми отчётами и RPC.
- При создании бронирования через новый RPC `hold_complex_slot`: запись в `bookings` + вставка строк в `booking_services`; `bookings.service_id` = первая услуга из списка.

**RLS:** доступ к `booking_services` наследуется от доступа к `bookings` (клиент видит только свои бронирования; дашборд — по своему бизнесу).

### 3.3 Доменная модель (core-domain)

- **Типы (`packages/core-domain/src/booking/types.ts`):**
  - `BookingServiceItem`: `{ service_id: string; duration_min: number; order_index?: number; price_from?: number; price_to?: number }`.
  - `CreateBookingParams`: добавить поле `services: BookingServiceItem[]`; сохранить `service_id` как опциональное (если передан один элемент — можно выставить `service_id` из него для совместимости).
  - `CreateGuestBookingParams`: аналогично.
  - `BookingDto`: добавить `services: BookingServiceItem[]`; при чтении из БД — заполнять из `booking_services` при наличии, иначе `[{ service_id, duration_min }]` из одной строки `bookings`.

- **Валидация:** непустой массив `services`, все `service_id` принадлежат одному бизнесу; суммарная длительность в разумных пределах (например, не более 8 часов); при необходимости — проверка, что все услуги может выполнить один и тот же мастер (по `service_staff`).

## 4. Слоты и RPC

### 4.1 Расчёт слотов для комплекса

- **Новый RPC** (например, `get_free_slots_complex_day_v1`):
  - Вход: `p_biz_id`, `p_branch_id`, `p_staff_id` (или null — «любой»), `p_day`, `p_duration_min` (суммарная длительность в минутах), `p_step_min` и т.п.
  - Логика: аналогично `get_free_slots_service_day_v2`, но слот считается свободным, если мастер свободен на **целиком** интервал длиной `p_duration_min`.
  - Возврат: тот же формат слотов (интервалы `start_at`, `end_at`), чтобы фронт и фильтрация по контексту не менялись.

- **Существующий RPC** `get_free_slots_service_day_v2`: остаётся для режима «одна услуга»; фронт вызывает его при `serviceIds.length === 1`, иначе — новый RPC с суммарной длительностью.

### 4.2 Создание бронирования (hold + confirm)

- **Новый RPC** `hold_complex_slot`:
  - Вход: `p_biz_id`, `p_branch_id`, `p_staff_id`, `p_start_at`, `p_services` (JSON/массив: `[{ service_id, duration_min, order_index }]`).
  - Проверка: интервал `[p_start_at, p_start_at + sum(duration_min)]` свободен у данного мастера в филиале.
  - Действия: вставка одной строки в `bookings` (в т.ч. `service_id` = первая услуга, `start_at`/`end_at` по суммарной длительности); вставка строк в `booking_services`.
  - Возврат: `booking_id`.

- **Существующие** `hold_slot` / `hold_slot_guest`: не трогаем; используются при одной услуге. API-роуты могут вызывать либо старый hold (одна услуга), либо новый `hold_complex_slot` (несколько).

## 5. Промо и пакеты визитов

- **Промо:** применение к бронированию как к одному визиту. Правила, привязанные к `service_id`, можно трактовать так: «применить, если в составе бронирования есть эта услуга» (например, к первой подходящей или к общей сумме). Конкретизация — в отдельном подзадаче при реализации промо-модуля.
- **Пакеты визитов:** один визит с несколькими услугами = одно списание с пакета; привязка пакета к «услуге» может означать «любая из выбранных услуг подходит под условие пакета».

    **Принятое правило (MVP):**

    - `bookings.service_id` остаётся **primary_service_id** и всегда указывает на **первую услугу** в составе `services[]`.
    - **Пакеты визитов** (см. `SUBSCRIPTIONS_AND_PACKAGES_FEATURE.md`):
        - продолжают отбираться по `service_id` (primary_service_id) и филиалу;
        - при многопозиционном визите **списывают 1 визит** и применяют свои ценовые правила **к этой основной услуге**; остальные услуги оплачиваются по базовой цене.
    - **Промоакции**:
        - действуют на **итоговую сумму визита**, рассчитываемую на стороне промо-логики как сейчас (через `promotion_applied.final_amount` и связанные поля), где базовая сумма визита включает все услуги комплекса;
        - для обратной совместимости `promotion_applied` продолжает ссылаться на `service_id` как на основную услугу, но аналитика может опираться на `service_ids`/`services_count` из funnel-событий.

## 7. Риски и ограничения

- **Производительность слотов:** новый RPC для комплексов должен учитывать суммарный интервал; при больших длительностях (например, 3+ часа) количество свободных слотов может уменьшаться — это ожидаемо.
- **Обратная совместимость:** все существующие интеграции, отчёты и кабинеты должны корректно работать с бронированиями, у которых есть только `bookings.service_id` и одна строка в `booking_services` (или даже без строк, если миграция старых данных не делается).
- **Промо/пакеты:** точные правила применения к многопозиционным визитам нужно согласовать с продуктом и описать в коде/документации, чтобы не было двойных скидок или некорректного списания визитов пакета.
