## Инварианты `user_current_business`

Документ описывает гарантии и ожидаемое поведение вокруг таблицы `user_current_business` и выбора «текущего бизнеса» в кабинете владельца/менеджера.

---

## 1. Назначение и модель

- Таблица `user_current_business` хранит **одну запись на пользователя**, отражающую его текущий активный бизнес в кабинете.
- Это технический кэш «последнего выбора», который:
  - используется при логине и редиректах (куда вести после `/`);
  - подаётся на вход `resolveBizContextForManagers` / `withManagerContext` как кандидат `bizId`;
  - не заменяет собой проверку ролей и прав — это всегда отдельная проверка.

---

## 2. Базовые инварианты

1. **Не более одной записи на пользователя**
   - Для каждого `user_id` в `user_current_business` допускается максимум одна строка.
   - Миграции и сервисные скрипты должны устранять дубликаты (оставляя последнюю/валидную запись).

2. **Текущий бизнес должен быть доступен пользователю как минимум по одной «управляющей» роли**
   - владелец (`businesses.owner_id = user_id`);
   - администратор/менеджер (`user_roles` / staff‑роль с ключом из набора `MANAGER_ROLE_KEYS`);
   - (опционально) другие роли, явно добавленные в `MANAGER_ROLE_KEYS`.

3. **Запрещены «висящие» ссылки**
   - `user_current_business.biz_id` обязан указывать на существующую запись в `businesses`;
   - при удалении/отключении бизнеса либо:
     - запись в `user_current_business` удаляется,
     - либо переводится на другой бизнес согласно политике (см. ниже).

4. **Несоответствие ролям трактуется как потеря доступа**
   - если пользователь теряет все управляющие роли к бизнесу из `user_current_business` (смена `owner_id`, удаление `user_roles`/staff‑записей), этот бизнес должен считаться недоступным;
   - при следующем входе нужно заставить пользователя выбрать новый активный бизнес (или показать пустое состояние, если бизнесов больше нет).

---

## 3. Поведение при логине и смене бизнеса

### 3.1. Первый логин / отсутствие записи

- Если у пользователя **нет записи** в `user_current_business`:
  - при наличии **одного** доступного бизнеса можно автоматически создать запись и сразу вести в `/dashboard`;
  - при наличии **нескольких** бизнесов:
    - не редиректить сразу в `/dashboard`;
    - показывать экран выбора (например, `/select-business`);
    - после выбора:
      - создать/обновить `user_current_business` (через единый серверный модуль/endpoint);
      - только затем редиректить в `/dashboard`.

### 3.2. Смена текущего бизнеса из UI

- Любая смена бизнеса из UI (дропдаун «Сменить бизнес» / `RoleAndBusinessSwitcher`) должна:
  - вызывать единый endpoint/функцию смены бизнеса;
  - проверять, что у пользователя есть права на выбранный `bizId` (как минимум owner/admin/manager);
  - атомарно обновлять `user_current_business`;
  - после успеха триггерить перезагрузку кабинета или мягкий reload данных.

---

## 4. Потеря прав к текущему бизнесу

Сценарии:

1. Пользователь больше не владелец (сменился `owner_id` в `businesses`).
2. Снята роль admin/manager/staff, которая давала доступ к бизнесу.
3. Бизнес деактивирован/удалён.

**Инвариант:** тихо **не** переключать пользователя на другой бизнес.

Ожидаемое поведение:

- очистить/обновить запись `user_current_business` при следующей проверке контекста;
- показать пользователю:
  - экран выбора нового бизнеса (если остаются другие доступные бизнесы),
  - либо понятный экран «у вас больше нет доступа к этому бизнесу»;
- требовать явного выбора нового активного бизнеса, прежде чем пускать в `/dashboard`.

---

## 5. Использование в коде

- `resolveBizContextForManagers` и `withManagerContext` должны:
  - сначала читать `user_current_business` как источник «последнего выбора»;
  - далее пересекать его с актуальными правами (owner + роли) и бизнесами;
  - если `bizId` из `user_current_business` невалиден — игнорировать его и запускать логику выбора:
    - единственный доступный бизнес → выбрать его;
    - несколько бизнесов → требовать выбора (экран/редирект).

- Любые миграции/скрипты (`backfill_user_current_business` и т.п.) должны:
  - соблюдать инвариант «одна запись на пользователя»;
  - не записывать в `user_current_business` бизнесы, к которым у пользователя нет прав;
  - при изменении схемы ролей пересчитывать записи в соответствии с актуальными правилами.

---

## 6. План дальнейших шагов

1. **Единый модуль смены текущего бизнеса**
   - Выделить серверную функцию/endpoint, которая:
     - принимает `bizId`;
     - проверяет права пользователя на этот бизнес;
     - обновляет/создаёт запись в `user_current_business`.
2. **Проверка миграций и backfill‑скриптов**
   - Пересмотреть существующие миграции, которые создают/изменяют `user_current_business`;
   - при необходимости добавить корректирующую миграцию, вычищающую дубликаты и «висящие» записи.
3. **Тесты на выбор бизнеса**
   - Покрыть unit‑тестами основные сценарии:
     - только `owner_id`;
     - только роли (admin/manager);
     - несколько бизнесов;
     - потеря ролей;
     - `super_admin` без текущего бизнеса.
