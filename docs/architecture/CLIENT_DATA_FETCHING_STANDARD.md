# Стандарт client-side data fetching

**Статус:** актуален  
**Цель:** закрепить единый подход к загрузке, кешированию и обновлению серверных данных на клиенте в `apps/web` и `apps/mobile`.

---

## 1. Базовое правило

`React Query` является стандартным и предпочтительным способом работы с server state на клиенте.

Это означает:

- для чтения серверных данных по умолчанию используются `useQuery` / `useInfiniteQuery`;
- для изменений используются `useMutation`;
- повторное использование данных, фоновые обновления и invalidation должны идти через query layer, а не через локальные `Map`, ручные `useEffect + fetch` и разрозненные `useRef`-кеши.

---

## 2. Когда ручной кеш допустим

Ручное кеширование допускается только как редкое исключение, если одновременно выполняются все условия:

- есть подтвержденный hot path или очень чувствительный к latency сценарий;
- `React Query` в текущем виде не покрывает сценарий без заметного усложнения или деградации UX;
- у исключения явно описаны владелец кеша, TTL/условия сброса и стратегия синхронизации;
- это решение зафиксировано в коде и, если участок критичный, в документации/аудите.

Типичные допустимые исключения:

- debounce/autosave orchestration для mutation-heavy сценариев;
- очень частый polling/runtime coordination, где query cache не является главным источником ценности;
- временный переходный слой до миграции на query abstraction.

---

## 3. Что считается нежелательным по умолчанию

Нежелательные паттерны в новом коде:

- `useEffect(() => { fetch(...) })` для обычного чтения данных без явной причины;
- локальный `Map`/`useRef`-кеш без documented invalidation strategy;
- дублирование одних и тех же серверных данных одновременно в `React Query` и в отдельном ручном кеше;
- ручной retry/loading/error lifecycle там, где его уже умеет query layer.

---

## 4. Практическое правило выбора

Если это обычный server state, нужно начинать с `React Query`.

Сценарии, которые по умолчанию должны идти через `React Query`:

- списки и детали сущностей;
- загрузка booking/staff/finance данных;
- мобильные экраны, которые читают данные из API/Supabase;
- prefetching данных для следующих экранов или шагов;
- cache invalidation после mutation.

Сценарии, которые могут остаться вне `React Query`, но требуют явного обоснования:

- сложный autosave с optimistic local workflow;
- узкоспециализированный slot loader с debounce, short-lived cache и агрессивной защитой от лишних запросов;
- bridge-слой в legacy feature до поэтапной миграции.

---

## 5. Текущая договоренность по проекту

В проекте `React Query` уже является фактическим базовым путем и должен считаться официальным стандартом.

Это уже видно в:

- `apps/web/src/lib/react-query.tsx`
- `apps/web/src/app/b/[slug]/hooks/useBookingData.ts`
- `apps/web/src/app/staff/finance/hooks/useFinanceData.ts`
- `apps/mobile/src/screens/HomeScreen.tsx`
- `apps/mobile/src/screens/ShiftQuickScreen.tsx`
- `apps/mobile/src/screens/BookingDetailsScreen.tsx`

Основной известный кандидат-исключение сейчас:

- `apps/web/src/app/b/[slug]/hooks/useSlotsLoader.ts`

Его пока допустимо оставлять как переходное исключение, но он должен рассматриваться как специальный случай, а не как шаблон для нового кода.

---

## 6. Требования к исключениям

Если участок всё же не использует `React Query`, в нём должно быть понятно:

- почему query abstraction здесь не взята;
- кто владеет кешем;
- когда кеш инвалидируется;
- как предотвращаются гонки и устаревшие данные;
- является ли решение временным переходным слоем.

Для критичных участков это нужно дополнительно фиксировать в audit/roadmap документе.

---

## 7. Следующая волна работ

После закрепления стандарта следующий практический шаг:

1. проверить, где ручное кеширование действительно необходимо;
2. там, где оно не даёт реальной пользы, перевести код на `React Query`;
3. отдельно рассмотреть `useSlotsLoader.ts`, `useQuickDeskClient.ts` и другие hot-path hooks как кандидаты на точечную миграцию или официально оформленные исключения.
