# Целевая модель работы с датами

Документ фиксирует, как в приложении хранятся даты, в какой таймзоне интерпретируются «календарные» даты и как фронт с бэкендом обмениваются датами.

---

## 1. Два типа данных

| Тип | Примеры полей | Смысл | Хранение |
|-----|----------------|--------|-----------|
| **Календарная дата (без времени)** | `valid_from`, `valid_to`, `shift_date`, даты акций, «сегодня» для смен | День в календаре бизнеса (без привязки к часу) | Строка **YYYY-MM-DD** или тип `date` в БД. Не хранить как UTC-полночь. |
| **Момент времени (timestamp)** | `start_at`, `end_at`, `created_at`, `opened_at`, `closed_at` | Конкретный момент в времени | **UTC**, в БД — `timestamptz`; в API — ISO 8601 (например `2025-03-05T14:00:00.000Z`). |

---

## 2. Таймзона для «календарных» дат

- **Эталонная таймзона:** по умолчанию **Asia/Bishkek** (`NEXT_PUBLIC_TZ`).
- Если у бизнеса в БД задана своя таймзона — использовать её (`getBusinessTimezone(businessTz)` из `lib/time.ts`) для «сегодня», границ суток и отображения.
- «Сегодня» и любые границы суток (начало/конец дня) на бэкенде считать через **`formatInTimeZone(now, tz, 'yyyy-MM-dd')`** (или `todayTz(tz)` из `lib/time.ts`), а **не** через `new Date().toISOString().slice(0, 10)` (то есть не UTC-дату).

---

## 3. Хранение календарных дат (valid_from, valid_to и т.п.)

- В БД хранить как **дату без времени**: тип `date` или строка **YYYY-MM-DD**.
- Интерпретация: эта дата — **календарный день в таймзоне бизнеса** (или в `NEXT_PUBLIC_TZ`), без перевода в UTC-полночь.
- При записи в БД **не** делать `new Date(value).toISOString().split('T')[0]` для произвольных datetime-строк (риск сдвига на день). Если с фронта приходит только **YYYY-MM-DD** — сохранять строку как есть или парсить только дату (например, взять подстроку YYYY-MM-DD).

---

## 4. Обмен фронт ↔ бэкенд

| Направление | Календарная дата (YYYY-MM-DD) | Timestamp |
|-------------|-------------------------------|-----------|
| **Фронт → API** | Строка **YYYY-MM-DD** (например из `<input type="date">`). Не передавать datetime без указания таймзоны (например без `Z`). | ISO 8601 с суффиксом (например `Z` или offset). |
| **API → фронт** | Строка **YYYY-MM-DD**. | ISO 8601 (UTC). |
| **Отображение на фронте** | По желанию: `toLocaleDateString(locale)` или `formatInTimeZone(date, tz, 'dd.MM.yyyy')` — при необходимости явно задать таймзону. | `formatInTimeZone(..., tz, 'dd.MM.yyyy HH:mm')` в таймзоне пользователя/бизнеса. |

---

## 5. Правила для бэкенда

- **«Сегодня»** (для проверок, фильтров, подстановки в записи):  
  `formatInTimeZone(new Date(), TZ, 'yyyy-MM-dd')` или `todayTz(TZ)` из `lib/time.ts`. ТZ брать из `getTimezone()` / `getBusinessTimezone(biz.timezone)`.
- **Приём даты из запроса:** если контракт — «только YYYY-MM-DD», сохранять подстроку/парсить только дату; не использовать `new Date(value).toISOString().split('T')[0]` для строк с временем без Z.
- **Диапазоны дат в аналитике/отчётах:** если период должен быть «по местному дню», считать границы через `formatInTimeZone` в нужной таймзоне; не привязывать границы суток к UTC без явного решения.

---

## 6. Правила для фронта

- Для выбора даты пользователем: **`<input type="date">`** → `e.target.value` даёт YYYY-MM-DD — отправлять в API как есть.
- Не отправлять в API «календарную дату» в виде datetime без таймзоны (например `2025-03-05T00:00:00`).
- При отображении дат из API (valid_from, valid_to и т.д.) можно использовать локаль пользователя; при необходимости единообразия с бэкендом — ту же таймзону (например `NEXT_PUBLIC_TZ`).

---

## 7. Сводка

| Вопрос | Решение |
|--------|---------|
| Как храним календарные даты (valid_from, valid_to, shift_date)? | **YYYY-MM-DD** (или тип `date` в БД), без времени. Не хранить как UTC-полночь. |
| В какой таймзоне «сегодня» и границы суток? | Таймзона бизнеса или **Asia/Bishkek** (`NEXT_PUBLIC_TZ`). На бэкенде — через `formatInTimeZone(..., tz, 'yyyy-MM-dd')`. |
| Как фронт передаёт даты в API? | Только **YYYY-MM-DD** для полей «календарная дата»; timestamps — ISO 8601 с Z/offset. |
| Как API возвращает даты? | Календарные даты — **YYYY-MM-DD**; моменты времени — **ISO 8601 (UTC)**. |

Дополнительно: [DATE_HANDLING_RISKS.md](DATE_HANDLING_RISKS.md) — найденные риски и места с `toISOString().split('T')[0]` / `slice(0, 10)`.

## 8. Актуальный статус модели

Эта модель уже частично закреплена в коде:

- `withManagerContext` поднимает `businessTz` в manager API;
- `getStaffContext` поднимает `businessTz` в staff API;
- high-risk `shift` и `finance` API уже переведены с глобального `TZ` на timezone бизнеса;
- `dashboard booking` и `cabinet booking` сценарии уже используют timezone бизнеса там, где она доступна из данных бизнеса/записи.

Это означает, что для новых day-based сценариев `businessTz` нужно считать обязательной частью контекста, если бизнес уже определён в момент выполнения сценария.
