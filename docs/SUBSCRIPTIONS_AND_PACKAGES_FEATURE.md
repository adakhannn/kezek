# Абонементы и пакеты визитов — описание фичи и план реализации

Документ описывает фичу **абонементов и пакетов визитов** для платформы Kezek: назначение, границы, модель данных и пошаговый список задач для реализации.

**Связанные документы:**  
`SYSTEM_FEATURES_DOCUMENTATION.md` (промоакции, бронирование, статусы), `docs/GLOSSARY.md` (термины).

---

## 1. Описание фичи

### 1.1 Назначение

Дать салонам и барбершопам возможность продавать клиентам **пакеты визитов** (например, «5 стрижек со скидкой») или **абонементы на период** (например, «безлимит маникюр в течение месяца»). При фактическом посещении (перевод брони в статус `paid`) визит списывается с пакета или абонемента; при необходимости применяется скидка или фиксированная цена по правилам пакета.

**Цели:**
- Увеличение удержания клиентов за счёт предоплаты и привязки к салону.
- Удобство для клиента: один раз купил пакет — визиты списываются автоматически.
- Гибкость для бизнеса: настраиваемые типы пакетов (N визитов, срок действия, привязка к услуге/филиалу или «любая услуга»).

### 1.2 Кто пользуется

| Роль | Действия |
|------|----------|
| **Владелец / Админ / Менеджер** | Создание типов пакетов (название, кол-во визитов, срок, скидка/фикс. цена, привязка к услуге/филиалу). Продажа пакета выбранному клиенту. Просмотр проданных пакетов и остатков. |
| **Клиент** | Просмотр своих активных пакетов и остатка визитов в личном кабинете. При записи и посещении — автоматическое списание визита при переводе брони в `paid`. |
| **Сотрудник (мастер)** | Видит в контексте записи/смены, что у клиента есть пакет (опционально). Фактическое списание выполняет система при `mark-attendance` / закрытии смены. |

### 1.3 Границы фичи

- **В рамках фичи:** типы пакетов (шаблоны), продажа пакета клиенту (остаток визитов, срок действия), списание визита при `paid`, отображение остатков в кабинете клиента и в дашборде.
- **Взаимодействие с промоакциями:** при переводе брони в `paid` должна быть однозначная политика: либо сначала проверяется пакет, либо промо. Рекомендуется: **сначала пакет** (если у клиента есть подходящий активный пакет с остатком — списываем визит и применяем условия пакета), иначе — существующая логика промо (`update_booking_status_with_promotion`). Двойные скидки (пакет + промо на одну запись) по умолчанию не применяются, если не задано иное правило.
- **Вне скоупа на первом этапе:** автоматическое напоминание «осталось N визитов», биллинг продления абонементов, пакеты «безлимит на период» (можно добавить в этапе 2).

### 1.4 Ключевые сценарии

1. **Владелец создаёт тип пакета:** «5 стрижек», 90 дней, скидка 10% с каждой услуги или фиксированная цена за визит.
2. **Владелец продаёт пакет клиенту:** выбор клиента, выбор типа пакета → создаётся запись «у клиента X пакет Y, остаток 5 визитов, до даты Z».
3. **Клиент записывается и приходит:** бронь переводится в `paid` → система проверяет активный пакет клиента по филиалу/услуге, списывает 1 визит, при необходимости пересчитывает сумму по правилам пакета и пишет в `bookings` факт использования пакета (аналогично `promotion_applied`).
4. **Клиент смотрит кабинет:** видит «У вас пакет „5 стрижек“, осталось 3 визита до 01.06.2026».

## 2. Модель данных

### 2.1 Концепция

- **Тип пакета (шаблон):** привязка к бизнесу; название; количество визитов; срок действия (дней с момента продажи); правило оплаты: скидка % или фиксированная цена за визит; привязка к услуге (одна или «любая»), к филиалу (один, несколько или «все»).
- **Проданный пакет (экземпляр у клиента):** клиент, тип пакета, оставшееся количество визитов, дата окончания, дата покупки.
- **История списаний:** какая запись бронирования списала визит с какого пакета (связь `booking_id` ↔ пакет), для аудита и отчётов; в `bookings` — поле `subscription_applied` (jsonb) для отображения в UI.

Связь с существующей системой:
- При переводе брони в `paid`: сначала проверка пакета и списание; при отсутствии подходящего пакета — текущая логика промо (`update_booking_status_with_promotion`).

### 2.2 Схема БД (финальная)

**Enum:** `visit_package_discount_type` — `'percent'`, `'fixed_price'`.

**Таблица `visit_package_plans`:**
| Колонка | Тип | Описание |
|---------|-----|----------|
| id | uuid PK | |
| biz_id | uuid NOT NULL FK → businesses(id) ON DELETE CASCADE | |
| name_ru | text NOT NULL | |
| name_ky | text | |
| name_en | text | |
| visit_count | integer NOT NULL | Количество визитов в пакете |
| validity_days | integer NOT NULL | Срок действия в днях с момента продажи |
| discount_type | visit_package_discount_type NOT NULL | percent / fixed_price |
| discount_value | numeric(10,2) NOT NULL | Процент (0–100) или фикс. сумма за визит |
| service_id | uuid FK → services(id) ON DELETE SET NULL | null = любая услуга |
| branch_ids | uuid[] | Массив id филиалов; пустой или null = все филиалы |
| is_active | boolean NOT NULL DEFAULT true | |
| created_at, updated_at | timestamptz | |

**Индексы:** biz_id, is_active (partial where is_active = true).

**Таблица `client_visit_packages`:**
| Колонка | Тип | Описание |
|---------|-----|----------|
| id | uuid PK | |
| client_id | uuid NOT NULL FK → auth.users(id) ON DELETE CASCADE | |
| plan_id | uuid NOT NULL FK → visit_package_plans(id) ON DELETE RESTRICT | |
| remaining_visits | integer NOT NULL | Остаток визитов |
| valid_until | date NOT NULL | Дата окончания действия |
| purchased_at | timestamptz NOT NULL DEFAULT now() | |
| created_at | timestamptz NOT NULL DEFAULT now() | |

**Индексы:** (client_id, valid_until) для выборки активных пакетов клиента; plan_id; (client_id, plan_id) для проверки дублей при продаже при необходимости.

**Таблица `client_visit_package_uses`:**
| Колонка | Тип | Описание |
|---------|-----|----------|
| id | uuid PK | |
| client_visit_package_id | uuid NOT NULL FK → client_visit_packages(id) ON DELETE CASCADE | |
| booking_id | uuid NOT NULL FK → bookings(id) ON DELETE CASCADE | UNIQUE — один booking = одно списание |
| used_at | timestamptz NOT NULL DEFAULT now() | |

**Индексы:** booking_id (unique), client_visit_package_id.

**Таблица `bookings` (дополнение):**
| Колонка | Тип | Описание |
|---------|-----|----------|
| subscription_applied | jsonb | При применении пакета: plan_id, plan_name, remaining_after, final_amount и т.д. |

**RLS:**
- `visit_package_plans`: владелец/админ/менеджер по biz_id (как у branch_promotions); публичное чтение активных — опционально.
- `client_visit_packages`: клиент видит только свои (client_id = auth.uid()); дашборд — SELECT по biz через join с visit_package_plans; INSERT только дашборд (через API с проверкой прав).
- `client_visit_package_uses`: клиент — SELECT по своим пакетам; дашборд — SELECT по biz через пакет и план.

## 4. Этапы и приоритеты

- **Этап 1 (модель данных)** — обязателен первым; от него зависят все остальные.
- **Этапы 2 и 3** — бэкенд: без списания при paid фича неполная, поэтому 2 и 3 идут подряд.
- **Этап 4 (дашборд)** и **Этап 5 (кабинет клиента)** — можно распараллелить после 3.
- **Этап 6** — тесты и документация желательно вести по ходу (после 2–3 — тесты бэкенда, после 4–5 — E2E при необходимости).

**Минимальный первый релиз:** этапы 1, 2, 3, 4.1–4.4, 5.1–5.2, 6.1–6.2 и 6.4 (пакеты без скидок — только списание визитов и отображение остатков; скидки и фикс. цена — при наличии полей в плане).
