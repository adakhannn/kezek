# Задачи: дебаунс-сохранение клиентов смены (batch save)

Документ описывает доскональный анализ текущего состояния и список задач для внедрения фичи «сохранение с дебаунсом»: сотрудник/владелец заполняет несколько клиентов подряд, данные уходят на сервер одним запросом после паузы в вводе (а не после каждого поля или каждой строки).

---

## 1. Текущее состояние (анализ)

### 1.1 Два потока данных, один не используется

| Место | Роль | Сохранение | Добавление клиента | Удаление |
|-------|------|------------|--------------------|----------|
| **FinancePage** (`staff/finance/components/FinancePage.tsx`) | Используется на `/staff/finance` и `/dashboard/staff/[id]/finance` | Только по кнопке «Сохранить» в форме (`handleSaveItem` → `mutations.saveItems(localItems)`). Дебаунса нет. | Локально в `localItems`, затем пользователь должен нажать «Сохранить» по форме. | Оптимистичное удаление из списка + немедленный `mutations.saveItems(updatedItems)`. |
| **useShiftItems** (`staff/finance/hooks/useShiftItems.ts`) | **Нигде не импортируется** | Дебаунс 20 с, один запрос после паузы. | Только локально; уходит в том же отложенном запросе. | Немедленный POST оставшихся items (отдельный запрос). |

Итог: изменения с дебаунсом 20 с и «добавить клиента без запроса» сделаны в `useShiftItems`, который в приложении не используется. Реальный UX по-прежнему «сохранять по кнопке» и «удаление = сразу запрос».

### 1.2 Где что вызывается

- **Страницы:**  
  - `apps/web/src/app/staff/finance/page.tsx` → `<FinancePage />` (сотрудник).  
  - `apps/web/src/app/dashboard/staff/[id]/finance/StaffFinancePageClient.tsx` → `<FinancePage staffId={id} />` (владелец).
- **FinancePage:** свой state `localItems`, синхронизация с `financeData.data?.items`, мутации `useFinanceMutations` (`saveItems`, `closeShift` и т.д.). Кнопка «Сохранить» в форме → `handleSaveItem` → `mutations.saveItems(localItems)`.
- **useShiftItems:** не импортируется ни в FinancePage, ни в других компонентах.

### 1.3 Проблемы текущего «быстрого» решения

1. Фича реализована в неиспользуемом хуке — поведение в проде не изменилось.
2. Дублирование логики: два места с фильтрацией «что сохранять», дедупликацией, вызовом API.
3. В используемом потоке (FinancePage) нет дебаунса: нельзя «заполнить трёх клиентов и отправить одним запросом» без трёх нажатий «Сохранить».
4. Нет явного индикатора «есть несохранённые изменения» и кнопки «Сохранить сейчас» в едином стиле с дебаунсом.
5. `addingClient` в `useShiftItems` после упрощения `addClient` больше не используется (всегда `false`).
6. Удаление в обоих вариантах — отдельный запрос; при желании можно рассмотреть включение удаления в тот же batch (опционально).

## 2. Целевое поведение

- **Дебаунс:** после последнего изменения (любое поле любого клиента или добавление/удаление строки) таймер N секунд (например, 15–20). По истечении — один `POST /api/.../shift/items` с полным списком items (все добавленные/изменённые/оставшиеся после удалений).
- **Добавление клиента:** только локальное добавление строки; на сервер уходит в том же отложенном запросе (или по «Сохранить сейчас»).
- **Удаление:** либо только локальное удаление из списка с последующей отправкой в том же batch, либо оставить немедленный запрос — решить в задачах.
- **«Сохранить сейчас»:** кнопка/действие, сбрасывающее таймер и сразу отправляющее текущий список (для тех, кто не хочет ждать N секунд).
- **Индикатор:** пока есть несохранённые изменения и не идёт запрос — показывать, что данные «не сохранены» и/или что через N с будет автосохранение (опционально — обратный отсчёт).

## 3. Список задач (по приоритету)

### Фаза 0: Подготовка и консистентность

- [x] **0.1** Решение зафиксировано: **единственный источник правды для клиентов смены — `FinancePage` и его состояние `localItems` + `useFinanceMutations`**. Хук `useShiftItems` сейчас нигде не используется и помечен как кандидат на удаление или полное переиспользование **после** того, как дебаунс и batch‑сохранение будут реализованы в реальном потоке (FinancePage) и дублирующая логика будет убрана.
- [x] **0.2** Проверено через поиск по коду: ни один компонент/хук не импортирует `useShiftItems`, есть только само определение файла `hooks/useShiftItems.ts`. Закомментированных/альтернативных веток с его использованием не найдено.

### Фаза 1: Внедрение дебаунса в используемый поток

- [x] **1.1** В FinancePage добавлено отложенное сохранение: при изменении `localItems` (в т.ч. после добавления/удаления клиента) запускается таймер `SAVE_DEBOUNCE_MS = 20_000`; при следующем изменении таймер сбрасывается; по срабатыванию один раз вызывается `mutations.saveItems(localItems)` (если смена открыта, режим не read‑only и текущая сигнатура списка отличается от последнего успешно сохранённого состояния). Явное сохранение и удаление клиентов сбрасывают таймер и обновляют сигнатуру, чтобы избежать двойных запросов.
- [x] **1.2** Сохранение по кнопке «Сохранить» в форме (`handleSaveItem`) по‑прежнему вызывает `mutations.saveItems(localItems)` и перед этим явно очищает `saveTimeoutRef`, так что после ручного сохранения не срабатывает отложенный автосейв с теми же данными.
- [x] **1.3** При размонтировании страницы (уход со страницы/закрытие вкладки) добавлен best‑effort flush: в `FinancePage` в cleanup‑`useEffect` берётся последний `localItems` и его сигнатура; если список не пустой, отличается от `lastSavedItemsRef.current`, смена открыта и не read‑only, вызывается `mutations.saveItems(latestItems)` без ожидания результата. Это минимизирует шанс потерять последние правки при уходе со страницы, не усложняя UX предупреждениями.
- [x] **1.4** При переключении с вкладки «Клиенты» на «Смена» или «Статистика» добавлен flush: в `useEffect` по `activeTab` при смене с `clients` сбрасывается таймер дебаунса и при наличии несохранённых изменений (сигнатура отличается от `lastSavedItemsRef`) вызывается `mutations.saveItems(latestItems)`. Учитываются те же условия (смена открыта, не read‑only).

### Фаза 2: UX и индикация

- [x] **2.1** Флаг «есть несохранённые изменения» технически реализован через связку `currentItemsSignatureRef` и `lastSavedItemsRef` в `FinancePage`: текущая сигнатура `localItems` (`serializeShiftItems(localItems)`) всегда хранится в `currentItemsSignatureRef`, а последняя успешно сохранённая сигнатура — в `lastSavedItemsRef`. Условие `currentItemsSignatureRef.current !== null && currentItemsSignatureRef.current !== lastSavedItemsRef.current` даёт точный признак наличия несохранённых изменений и уже используется в логике дебаунса/flush; дальше его можно будет напрямую подвязать к UI-индикаторам.
- [x] **2.2** В шапке списка клиентов (`ClientsListHeader`) рядом с заголовком «Клиенты за смену» выводится индикатор «Изменения не сохранены» (amber), если `hasUnsavedChanges` и не идёт сохранение; подсказка по hover — «Будет сохранено автоматически через несколько секунд». Ключи i18n: `staff.finance.clients.unsaved`, `staff.finance.clients.unsavedHint` (ru, en, ky).
- [x] **2.3** В шапке списка клиентов добавлена кнопка «Сохранить сейчас»: если есть несохранённые изменения, она видна и при нажатии очищает таймер дебаунса и вызывает `mutations.saveItems(latestItems)` из `FinancePage`. После успешного сохранения обновляются `lastSavedItemsRef` и `lastSavedSignature`, чтобы индикатор и дебаунс корректно отражали новое состояние. Ключ i18n: `staff.finance.clients.saveNow` (ru, en, ky).

### Фаза 3: Удаление и консистентность операций

## 4. Технические заметки

- **API:** сохранение уже идёт одним запросом с полным списком items: `POST /api/staff/shift/items` (сотрудник) и эквивалент для dashboard (если есть). Менять контракт не требуется; важно только не слать лишние запросы (дебаунс) и при желании — объединять удаление в тот же batch.
- **Конфликт с синхронизацией:** после `saveItems` вызывается инвалидация/refetch в `useFinanceMutations`; при слиянии с `localItems` в FinancePage учесть, что новые элементы без `id` не должны теряться до ответа сервера (текущая логика с `skipNextSyncRef` и merge по `id` остаётся в силе).
- **Мобильный сценарий:** «в основном заполняют с телефона» — дебаунс 15–20 с уменьшает количество запросов при вводе и снижает риск лишних запросов при тряске/потере фокуса; кнопка «Сохранить сейчас» даёт контроль при нестабильной сети.
