# Проверка критичных исправлений, 10 ноября 2026

Статус: **исторический промежуточный снимок 10 ноября**. Пакет завершён и проверен 11 ноября: [итог](../engineering-2026-11-11-closure/summary.md). Наблюдения ниже сохраняют границу своей даты. Это отдельная инженерная итерация по прямому запросу владельца; старые WEB acceptance и automation не изменялись. LOCAL_FIXED и локальный PASS не означают применение миграций или готовность deployment.

## Исходная среда и совместимость

Владелец разрешил использовать связанный Supabase как тестовый и выбрал Vercel Pro / Enterprise. Через административный read-only доступ проверены PostgreSQL 17.4, история миграций, определения функций, ACL, RLS, индексы и ограничения. Получены частные резервные копии, содержащие исходную схему и данные; персональные данные и потенциально чувствительные function bodies не добавляются в репозиторий.

| Частный артефакт | SHA-256 |
| --- | --- |
| `remote-combined-schema.sql`, схемы public + auth | `f9f2410628ec05aa41cc8bf40ebde7647f9160e040d2c144566d5438c0aaf84c` |
| `remote-public-data.sql` | `86fea11218c92ed063b598da3d5902077e85c08bd9344cfbb515ee4525402591` |

Восстановление выполнено в отдельном PostgreSQL 17 контейнере, network=none, без опубликованных портов. Сохранялись реальные ограничения, триггеры и RLS. Для внешних ключей перенесены только восемь Auth UUID, без паролей, токенов или сессий. Исходные данные копии: три закрытые смены, две позиции, 30 броней. Проверочные финансовые/booking записи выполнены только в копии и откатились.

В рабочем Supabase миграции этого этапа **пока не применены**. История имеет два установленных расхождения, описанных в [порядке миграций](../../../supabase/APPLY_MIGRATIONS.md): эквивалентная июльская миграция записана другим номером, октябрьское тело функции уже действует без соответствующего номера. Слепой `db push --include-all` не выполнялся.

## Уже выполненные проверки на фактической схеме

| Проверка | Результат и граница |
| --- | --- |
| Save/revision/tenant/DML | PASS после 113000: null/null только для новой смены, повтор с устаревшей ревизией отклонён, прямой item DML и чужое финансовое чтение запрещены. Проверочные записи rollback |
| Атомарное создание брони | PASS: одна confirmed booking, одна confirm outbox entry, стабильный receipt при повторе, другой guest proof/payload отклонён. Дополнительно PASS после service-only boundary. Проверочные записи rollback |
| Страницы слотов | PASS: анонимные ограниченные страницы в сумме равны полному привилегированному запросу реального расписания; старый анонимный all-staff вызов отклонён |
| Миграции reporting/backlog/cron | DDL replay PASS на восстановленной схеме. Это не полный нагрузочный или UI-тест |

Эти результаты относятся к проверенным snapshot файлов. Финальный последовательный replay всего набора, общие gates и source hashes ещё собираются; последующие изменения требуют адресной повторной проверки.

## Новое подтверждённое критичное условие

`cancel_booking(uuid)` в исходной удалённой схеме — SECURITY DEFINER, доступен PUBLIC/anon/authenticated/service_role. Тело делает UPDATE по ID для hold/confirmed/paid без проверки вызывающего. `confirm_booking(uuid)` также не проверял владельца. Это подтверждение небезопасной границы SQL, а не доказательство состоявшейся атаки. Реальные брони для проверки не менялись.

Исправление и отрицательные role cases ведутся в [123000](../../../supabase/migrations/20261110123000_service_only_booking_commands.sql). Публичные обходы должны быть закрыты независимо от HTTP middleware и rate limiter. Отмена оплаченной брони дополнительно требует согласованности с финансовым ledger.
